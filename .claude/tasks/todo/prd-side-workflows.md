# PRD: 크롤링과 따로 도는 워크플로우를 화면에서 관리한다

> 작성일: 2026-08-28
> 기준 버전: v0.1.0-8-gc53d1ea
> 근거: `app/classify/`, `app/normalize/backfill.py`, `.claude/docs/api-contract.md`,
> `seeds/site-configs-20260826.json`

## 목표

크롤링과 별개로 도는 작업 — LLM 분류, 스프링 전달 — 을 한 화면에서 등록하고, **언제 무엇을
대상으로 돌지**를 설정하고, 실행 결과를 본다.

그리고 분류가 읽는 입력을 셀렉터가 뽑은 본문에서 **상세 원문 전체**로 바꾼다.

## 지금 상태 (2026-08-28)

| 작업 | 도는 방식 | 화면 | 실행 기록 |
|---|---|---|---|
| LLM 분류 | `POST /api/classify?limit=N` 를 직접 호출 | 없음 | 없음 |
| 재정규화 | `POST /ui/renormalize` | `/rules` 아래 패널 | 없음 |
| 스프링 전달 | 없음. 소비 측이 `GET /api/jobs` 로 가져간다 | 없음 | `delivered_at` 뿐 |
| 크롤링 | APScheduler + `workflows` | `/workflows` | `crawl_runs` |

분류는 화면이 없어 운영자가 직접 호출해야 하고, 진행 상황은 한 프로세스의 메모리라 서버가
다시 뜨면 사라진다 (`app/classify/batch.py`). 언제 얼마나 돌았는지 남는 곳이 없다.

### 분류 입력에 구멍이 있다

세 가지가 겹친다.

1. 정규화는 분류 결과가 있으면 열한 칸을 **빈 값까지 포함해 전부** 덮는다
   (`app/normalize/engine.py` 의 "여섯 칸은 수집이, 열한 칸은 분류가 가진다")
2. 분류는 `raw_jobs.raw_data_json.body` 하나만 읽는다 (`app/classify/store.py` 의 `_BODY`)
3. `seeds/site-configs-20260826.json` 기준 일곱 곳(SK·롯데·두산·네이버·토스·카카오·
   우아한형제들)이 `requirements` 와 `department` 를 상세에서 **따로** 뽑는다

그 값이 본문 밖 요소에 있으면 분류는 그것을 보지 못하고, 셀렉터가 제대로 뽑아 둔 값을 빈 값으로
덮는다. 몇 건이 실제로 그런지는 운영 DB 에서 세어야 한다 ("열려 있는 것").

## 비목표

- **스프링으로 실제 전송하는 것.** 이번 범위는 설정과 화면까지고, 아무것도 보내지 않는다
- **`delivered_at` 의 주인을 바꾸는 것.** 계약은 폴링인 채로 둔다
  (`.claude/docs/api-contract.md`). 푸시로 바꾸는 것은 그 문서와 구현을 한 커밋에서 같이 고치는
  별도 작업이다
- 부가 작업을 크롤 `workflows` 테이블에 합치는 것
- 사이트별 칸 매핑 되살리기. 2026-08-26 에 176번 판단으로 만들었다가 같은 날 뺐다
  (`seeds/site-configs-20260826.json` 의 `why_the_mappings_were_removed`)
- 재정규화를 이 화면으로 옮기는 것. `/rules` 의 패널을 그대로 둔다
- 분류 결과를 고치는 새 경로. 검수 화면의 보정이 이미 그 자리다

## 1. 부가 워크플로우는 표를 따로 쓴다

`workflows` 에 넣지 않는다. 이유가 셋이다.

`workflows.crawler_id` 는 `NOT NULL` 이고 분류에는 크롤러가 없다. `crawl_runs` 가 세는 것은
신규·건너뜀·실패인데 분류가 셀 것은 처리·버린 칸이고 전달이 셀 것은 전송 건수다. 그리고 이미
`app/api/classify.py` 와 `app/normalize/backfill.py` 가 "`crawl_runs` 에 쓰지 않는다,
섞으면 워크플로우 성공·실패 통계가 크롤링과 무관한 이유로 움직인다"를 결정으로 들고 있다.

```
side_workflows
  id, kind, name, status, trigger_kind, interval_minutes,
  target_scope, target_days, batch_limit, last_run_at, created_at

side_runs
  id, side_workflow_id, trigger, started_at, finished_at, status,
  target_count, processed_count, failed_count, note, error_message
```

| 컬럼 | 값 |
|---|---|
| `kind` | `classify` / `deliver` |
| `status` | `active` / `paused`. **새로 만들면 `paused` 다** |
| `trigger_kind` | `interval` / `after_crawl` / `manual` |
| `target_scope` | 종류마다 받는 값이 다르다. 아래 2·3 절 |
| `target_days` | `recent` 일 때만 쓴다. 그 밖에는 NULL |
| `batch_limit` | 1회 상한 건수 |

토큰 수는 이 표에 두지 않는다. `llm_calls` 가 호출마다 남기고 있고
(`app/llm/log.py`), 같은 숫자를 두 곳에서 세면 어느 쪽이 진실인지 매번 확인해야 한다.

스케줄러는 지금 쓰는 APScheduler 를 그대로 쓴다. `app/scheduler.py` 의 `sync()` 가 크롤 잡과
부가 잡을 함께 맞추고, 표가 진실이라는 규칙은 그대로다 (`.claude/rules/crawling.md`).

## 2. 분류 워크플로우

### 언제 도는가

| `trigger_kind` | 뜻 |
|---|---|
| `interval` | N 분마다 |
| `after_crawl` | 크롤 실행이 새 공고를 적재한 직후에만 |
| `manual` | 화면에서 누를 때만. 지금과 같다 |

`after_crawl` 은 적재 건수가 0 이면 돌지 않는다. 신규가 하루 0~1건이라 이 조건이 없으면 아무
대상도 없는 실행이 사이트 수만큼 쌓인다.

### 무엇을 대상으로 하는가

| `target_scope` | 대상 | 토큰 |
|---|---|---|
| `unclassified` | 아직 분류되지 않은 건. **기본값** | 밀린 만큼 |
| `empty_fields` | 분류는 했는데 열한 칸이 전부 빈 건 | 그 건수만큼 |
| `recent` | 최근 `target_days` 일 안에 수집된 건 | 그 건수만큼 |
| `all` | 이미 분류된 것까지 전부 다시 | **전량 재지출** |

`unclassified` 는 지금 `app/classify/store.py` 의 `pending_ids` 그대로다. 최근 수집분부터
도는 순서도 유지한다 (2026-08-27 결정).

`all` 과 `recent` 는 이미 있는 `job_classifications` 행을 덮어쓴다. 덮어쓴 뒤에도 사람이 넣은
`job_field_overrides` 는 그대로 살아 있다 — 정규화가 규칙 다음에 분류, 그다음에 보정 순으로
덮기 때문이다 (`app/normalize/engine.py`). 이 순서는 바꾸지 않는다.

### 폭주를 막는 것

- `batch_limit` 은 1회 상한이다. 기본 50, 상한 200 (`app/classify/batch.py` 의 `MAX_LIMIT`)
- **`all` 을 저장할 때 대상 건수를 세어 확인 창에 적는다.** 640건이면 약 285만 토큰이고,
  돌기 시작하면 멈출 수 없다
- 같은 워크플로우가 두 번 겹쳐 돌지 않는다. 돌고 있는 동안 들어온 실행은 건너뛰고 그 사실을
  `side_runs` 에 남긴다

## 3. 스프링 전달 워크플로우 (설정과 화면까지)

**아무것도 보내지 않는다.** 화면에 그 사실을 낱말로 적고, 실행 단추는 비워 둔다.

설정은 `app_settings` 에 키로 넣는다. 새 표를 만들지 않는다 — 알림 설정이 이미 그 방식이다
(`app/notify/settings.py`).

| 키 | 값 |
|---|---|
| `deliver_url` | 스프링이 받는 주소 |
| `deliver_method` | `POST` / `PUT` |
| `deliver_auth_header` | 헤더 이름과 값. 비워 둘 수 있다 |
| `deliver_batch_size` | 한 번에 보낼 건수 |

언제 보낼지는 `side_workflows` 행이 들고 있다. `trigger_kind` 는 분류와 같고 `target_scope` 는
`undelivered`(기본) / `recent` / `all` 이다.

**자격증명을 어떻게 줄지는 아직 정하지 않았다** (`.claude/docs/api-contract.md`). 이 화면은
운영자가 값을 넣어 둘 자리를 만들 뿐이고, 그 값을 실제로 쓰는 것은 계약을 정한 뒤다.

## 4. 원문을 그대로 저장하고 분류가 그것을 읽는다

수집할 때 상세의 내용을 **가공 없이** `raw_jobs.raw_data_json.source_text` 에 넣는다. 사람이
상세 페이지를 드래그해서 복사한 것과 같은 수준이다 — 태그는 없고 줄바꿈은 살아 있다.

범위는 **상세 컨테이너**다. `<body>` 전부가 아니다. GNB·푸터·추천공고까지 넣으면 근거 검사
(`app/classify/grounding.py`)가 "원문에 이 글자가 있나"로 판정하기 때문에 푸터의 회사 주소가
근무지로 통과한다.

**`content_hash` 에는 넣지 않는다.** 지금 해시는 `source_url`·`title`·`deadline`·`body` 넷이고
(`app/crawler/hashing.py`), 여기에 페이지 전체가 들어가면 조회수나 배너 하나에 같은 공고가 매
크롤마다 신규로 쌓인다.

분류는 `source_text` 를 읽고, 없으면 `body` 로 떨어진다. **폴백이 필수다** — 이미 쌓인 건에는
`source_text` 가 없고, 그것을 대상 조건에서 빼면 기존 공고가 통째로 분류에서 사라진다.

`MAX_BODY_CHARS` 는 지금 12,000 이고 2026-08-26 기준 최대 본문이 11,584자였다. 원문은 이보다
길다. 상한을 다시 정하고, 잘린 사실을 응답에 남기는 지금 동작은 그대로 둔다
(`app/classify/classifier.py`).

원문은 검수 모달에 읽기 전용으로 붙인다. 표에는 열을 늘리지 않는다 — 이미 스물세 개다.

## 5. 화면

새 화면 하나를 네비게이션에 더한다 (`app/api/ui.py` 의 `NAV`). 이름은 `부가 워크플로우` 다.

| 구역 | 내용 |
|---|---|
| 목록 | 종류·이름·상태·실행 시점·대상 범위·마지막 실행·최근 결과 |
| 등록·수정 | 위 설정 항목. `all` 을 고르면 대상 건수를 확인 창에 적는다 |
| 지금 실행 | 한 번 돌린다. 도는 동안 진행 상황을 폴링해 보여준다 |
| 실행 이력 | `side_runs` 최근 것부터. 대상·처리·실패·비고 |
| 스프링 전달 설정 | 주소·메서드·인증 헤더·1회 건수. 보내지 않는다는 사실을 적는다 |

상태는 낱말로 적는다. 아이콘도 이모지도 쓰지 않는다 (`.claude/rules/writing.md`).

## 6. 빈 칸을 채우고 틀린 칸은 제안한다

원문을 읽게 된 뒤의 목표는 **원문에 있는 것을 하나도 놓치지 않는 것**이다. 원문에 없는 것을
채우는 것은 목표가 아니다 — 그것은 채우는 것이 아니라 지어내는 것이고, 소비 측이 그것을
사실로 노출한다 (`.claude/rules/llm.md`).

세 가지를 가른다.

| 상황 | 어떻게 |
|---|---|
| 칸이 비어 있고 원문에 값이 있다 | 채운다. 지금 경로 그대로 `job_classifications` 로 간다 |
| 칸에 값이 있는데 원문과 다르다 | **제안으로 남긴다.** 자동으로 덮지 않는다 |
| 원문에도 없다 | 빈 칸으로 둔다 |

### 값이 있는 칸을 자동으로 덮지 않는 이유

수집이 채우는 여섯 칸이 대상에 들어오기 때문이다. `deadline` 은 마감 지난 공고를 상세에서
거르는 데 쓰이고 `company` 는 계열사를 가르는 값이다. 이 둘을 본문 판독이 덮으면, 사이트가
정확히 준 값이 모델 판단 하나로 바뀐다.

제안으로 두면 모델이 고칠 수 있으면서 멀쩡한 값이 조용히 바뀌지는 않는다. 모델은 제안자이지
권위가 아니다 (`.claude/rules/llm.md`).

### 어떻게 만드는가

호출에 **원문과 지금 값을 함께** 준다. 지금은 원문만 주고 칸을 채우게 하는데, 무엇이 이미
채워져 있는지 모르면 "다르다" 를 말할 수 없다.

```
job_field_suggestions
  id, raw_job_id, field_name, value, reason, created_at
```

`(raw_job_id, field_name)` 이 유일하다. 같은 칸에 제안이 둘이면 어느 것을 보고 있는지 알 수
없다. 새 제안은 옛 제안을 덮는다.

수락하면 `job_field_overrides` 에 들어간다 — 사람이 손으로 고친 값과 같은 자리다. 거절하면
제안 행만 지운다. 어느 쪽이든 `raw_jobs` 와 `normalized_jobs` 는 건드리지 않는다.

**빈 칸 채우기와 제안은 같은 호출 하나에서 나온다.** 두 번 부르면 토큰이 두 배다.

## 개발 순서

| Push | 내용 | 검증 |
|---|---|---|
| 1 | 마이그레이션 0016, `side_workflows`·`side_runs` 와 저장소 모듈 | 마이그레이션 up·down, 저장소 단위 테스트 |
| 2 | 분류 대상 범위 네 가지를 `app/classify/store.py` 에 더한다 | 픽스처 DB 에 범위별 대상 건수 단언 |
| 3 | 부가 워크플로우 실행기와 `side_runs` 기록. 분류만 붙인다 | 실행 1회가 행 하나를 남기는지, 겹쳐 돌지 않는지 |
| 4 | 스케줄러가 `interval` 을 등록한다. `sync()` 를 부가 잡까지 넓힌다 | 표를 바꾸면 잡이 따라오는지 |
| 5 | 화면: 목록·등록·수정·지금 실행·실행 이력 | 화면에서 만들고 돌려 본다 |
| 6 | `after_crawl` 트리거를 크롤 실행 끝에 붙인다 | 적재 0건이면 돌지 않는지 |
| 7 | 스프링 전달 설정 저장소와 화면. 보내지 않는다 | 값이 저장·검증되는지 |
| 8 | 원문 수집. `source_text` 저장, 해시 제외 | 픽스처로 원문이 들어가고 해시가 그대로인지 |
| 9 | 분류 입력을 `source_text` 로 바꾸고 `body` 폴백. 상한 재산정 | 원문 있는 건과 없는 건 둘 다 |
| 10 | 검수 모달에 원문을 읽기 전용으로 붙인다 | 화면 확인 |
| 11 | 빈 칸 채우기와 교정 제안. `job_field_suggestions` 와 검수 화면의 수락·거절 | 제안이 보정으로만 들어가는지 |

1~7 과 8~10 은 서로 기다리지 않는다. 8~10 을 먼저 해도 되고, 둘을 나눠 돌려도 된다.

**8~10 이 끝나도 이미 쌓인 건은 `body` 로 분류된다.** 원문 기준으로 바꾸려면 그 뒤에 재수집이
한 번 필요하고, 그것은 이 PRD 의 작업이 아니라 운영자가 워크플로우를 돌리는 일이다.

## 끝났다고 말할 수 있는 조건

1. 화면에서 분류 워크플로우를 만들고, 실행 시점과 대상 범위를 골라 저장할 수 있다
2. 저장한 워크플로우가 주기대로 돌고, 실행마다 `side_runs` 에 행이 하나 남는다
3. 크롤 실행이 새 공고를 적재했을 때만 `after_crawl` 분류가 이어 돈다. 0건이면 돌지 않는다
4. `all` 을 고르면 대상 건수가 확인 창에 나오고, 확인 없이는 저장되지 않는다
5. 크롤 워크플로우 화면과 `crawl_runs` 의 숫자는 이 작업 전후로 달라지지 않는다
6. 스프링 전달 설정을 저장하고 다시 열면 값이 남아 있다. 화면은 보내지 않는다고 적고 있다
7. 새로 수집한 건의 `raw_data_json.source_text` 에 상세 원문이 그대로 있고, 같은 공고를 다시
   크롤해도 `content_hash` 가 같아 신규로 쌓이지 않는다
8. 원문이 있는 건은 원문으로, 없는 건은 본문으로 분류된다
9. 비어 있던 칸이 원문에 값이 있으면 채워지고, 원문에도 없으면 비어 있는 채로 남는다
10. 값이 있는 칸은 어떤 경로로도 자동으로 덮이지 않는다. 제안이 뜨고, 수락해야 바뀐다

## 열려 있는 것

**셀렉터가 뽑은 값을 분류가 빈 값으로 덮은 건이 몇 건인가.** 코드와 시드에서 그렇게 될 수
있다는 것까지 확인했고, 실제 건수는 운영 DB 에서 세어야 한다. 4절의 이득이 얼마인지가 이
숫자다.

**원문의 실제 길이.** 열한 사이트의 상세 컨테이너 텍스트가 몇 자인지 재지 않았다.
`MAX_BODY_CHARS` 를 얼마로 올릴지가 여기 달려 있다.

**상세 컨테이너를 무엇으로 잡을 것인가.** 셀렉터를 하나 더 두는 것(사이트마다 판단이 는다)과
본문 셀렉터의 조상 요소를 쓰는 것 중 정하지 않았다. Push 8 에서 정한다.

**스프링이 받는 형식.** 주소·메서드·인증만 넣어 둘 자리를 만들고, 본문 모양은 소비 측이 붙을
때 정한다.
