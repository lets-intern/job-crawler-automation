### 8.1.V 누락·중복 없음

시드 150건을 **전부 같은 `normalized_at`** 으로 넣었다. 저장 형식이 초 단위라 한 실행에서
적재된 수십 건이 같은 값을 갖고 페이지 경계가 그 안쪽에 걸리는 것이 정상 상황이기 때문이다.

1페이지 100건에 `has_more` 참, 2페이지 50건에 거짓. 이어붙인 150건에서 중복 0, 시드 전체와
집합 일치, 순서까지 일치.

1페이지를 받은 뒤 더 앞선 시각의 행을 삽입해도 나머지 집합이 온전한지도 확인했다.
오프셋 기반이면 여기서 건너뛰는 건이 생긴다.

### 8.4.V delivered_at 불변

허수 통과를 배제한 것이 핵심이다. `datetime('now')` 는 초 단위라 같은 초에 덮어써도 값이 같아
그냥 통과해 버린다. 그래서 계약 경로로 전달 표시를 한 뒤 `delivered_at` 을 `2020-01-01` 로
돌려놨다. 어느 경로가 다시 쓰면 오늘 날짜로 바뀌어 즉시 드러난다.

그 상태에서 규칙 추가 후 재정규화하고 워크플로우를 1회 더 실행했다. 두 행 모두 `2020-01-01`
그대로였다. 재정규화가 실제로 `title` 의 개행을 없앤 것도 같이 확인해, 아무 일도 일어나지 않아서
통과한 것이 아님을 못박았다.

정적 감사도 넣었다. `app/` 전체 `.py` 를 훑어 `delivered_at` 에 쓰는 파일 목록이
`app/api/jobs.py` 하나인지 단언한다. 정규식이 실제로 그 파일을 잡아내므로 공허한 단언이 아니다.

**제거할 코드는 없었다.** 정규화 엔진의 INSERT 컬럼과 재정규화의 UPDATE SET 에 `delivered_at` 이
없고, 화면 라우터는 SELECT 만 한다.

## 계약 준수

`.claude/docs/api-contract.md` 를 그대로 구현하고 문서는 고치지 않았다.
응답 `items` 의 필드 9개를 정확히 단언하며 `delivered_at` 은 응답에 없다.
커서는 `(normalized_at, id)` 쌍의 base64 opaque 값이고 정렬도 같은 쌍의 오름차순이다. 오프셋 없음.
`normalized_at` 저장 형식은 손대지 않고 응답에서만 ISO 모양으로 옮긴다.

## 남은 일 — 계약 문서에 없는 것 세 가지

임의로 문서를 고치지 않았다. 소비 측이 참조할 값이라면 계약에 적어야 한다.

- `POST /api/jobs/delivered` 의 응답 모양이 문서에 없다. 구현은
  `{"marked", "already_delivered", "missing"}` 을 돌려준다. 없는 id 하나로 배치 전체를 실패시키면
  소비 측이 나머지를 다시 받게 되므로 `missing` 으로 보고하는 쪽을 택했다
- `GET /api/jobs` 는 마지막 페이지에서도 `next_cursor` 를 비우지 않고 마지막 위치를 돌려준다.
  폴링 재개 위치를 보존하기 위해서다. `has_more: false` 가 더 받을 것이 없음을 알린다
- 오류 응답 절이 문서에 없다. 망가진 `cursor` 는 400, 잘못된 `updated_after` 는 422 로 거절한다.
  조용히 처음부터 주면 소비 측이 전량을 다시 받는다
