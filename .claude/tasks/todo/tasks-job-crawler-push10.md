## 왜 별도 저장소가 필요한가

이 Push 의 전부가 여기에 달려 있다.

사람이 고친 값을 `normalized_jobs` 에 그대로 쓰면, 다음 재정규화가 규칙으로 그 컬럼을 다시
덮어쓴다. 검수에 들인 시간이 버튼 한 번에 사라진다. `.claude/rules/data-safety.md` 가
`raw_jobs` 를 append-only 로 둔 것과 같은 이유가 여기에도 적용된다.

**사람의 보정은 파생값이 아니라 출처다.** 규칙이 만든 값과 같은 자리에 두면 안 된다.

| 층 | 저장 위치 | 성격 |
|---|---|---|
| 수집 | `raw_jobs.raw_data_json` | append-only. 아무도 고치지 않는다 |
| 규칙 | `normalization_rules` | 운영자가 고친다. 전체에 적용된다 |
| 사람 보정 | `job_field_overrides` (신규) | 운영자가 고친다. 공고 하나의 필드 하나 |
| 확정 | `normalized_jobs` | 위 셋에서 매번 다시 만들어진다 |

적용 순서는 규칙 다음에 보정이다. 규칙을 개선하면 보정하지 않은 필드는 같이 좋아지고,
보정한 필드는 사람이 정한 값을 유지한다. 둘 다 살아남는 유일한 배치다.

## 전달 상태를 건드리지 않는다

`.claude/rules/data-safety.md` 는 수동 수정이 `delivered_at` 을 지우거나 되돌리는 것을 금지한다.
소비 측에 같은 데이터가 다시 가기 때문이다.

따라서 이미 전달된 행을 고쳐도 소비 측은 옛 값을 그대로 갖는다. **검수는 전달 전에 하는 것이
정상 경로다.** 화면 기본 정렬을 미전달 우선으로 두는 이유가 이것이다.

전달 후 정정을 소비 측에 반영하는 방법은 계약 변경이 필요한 사안이라 이 Push 범위 밖이다.

## 페이징 방식

이 화면은 오프셋 기반 페이지 번호를 쓴다. 사람이 3페이지를 다시 열 수 있어야 하고, 전체
페이지 수가 보여야 한다.

제공 API(Push 8)의 커서 기반과 다른 것은 의도된 차이다. 그쪽은 폴링 사이 삽입된 행 때문에
건너뛰는 건이 생기면 안 되고, 이쪽은 사람이 보는 화면이다.
