# PRD: 직무를 정해진 분류 체계로 나눈다

> 작성일: 2026-08-28
> 기준 버전: `feat/fields-and-logo` (fields-and-logo 7 Push 완료 시점)
> 근거: `seeds/job-taxonomy-zighang-20260828.json`, `.claude/rules/llm.md`

## 목표

LLM 이 공고를 **운영자가 등록한 직무 분류 체계에서 골라** 나눈다. 체계는 코드가 아니라 표에
있고, 어드민에서 더하고 고치고 감춘다.

## 지금 상태

`job_category`(직군, 닫힌 목록 15개)는 fields-and-logo Push 1 이 지웠고, 그 자리에 Push 2 가
`job_role`(직무, **제목에서 뽑는 자유 텍스트**)을 넣었다.

그래서 **지금 소비 측이 직무로 거를 수 있는 값이 없다.** 자유 텍스트는 `백엔드 개발자`,
`Backend Engineer`, `서버개발` 로 흩어지고 그것으로는 필터가 서지 않는다. 거를 수 있는 판정
칸은 `employment_type`(고용형태)과 `career_level`(경력 구분) 둘뿐이다.

할 수도 있다. **그래서 표에 두고 어드민에서 고친다.**

## 비목표

- 분류 체계를 코드 상수로 두는 것. 그러면 사이트가 늘 때마다 배포해야 한다
- 소분류를 우리가 새로 설계하는 것. 씨앗을 쓰고 운영하며 고친다
- 한 공고에 직무를 여럿 다는 것. 하나다 (태그는 2026-08-28 에 범위에서 뺐다)
- `job_role`(제목에서 뽑는 자유 텍스트)을 지우는 것. 둘은 다른 값이고 함께 간다
- 이미 분류된 건을 자동으로 다시 도는 것. 재분류는 부가 워크플로우 화면에서 운영자가 건다
  (`prd-side-workflows.md`)

## 1. 표

```
job_taxonomy
  id, parent_id, name, sort_order, enabled, note, created_at, updated_at
```

한 표에 대분류와 소분류를 함께 둔다. `parent_id` 가 NULL 이면 대분류다. 표를 둘로 가르면
같은 CRUD 를 두 벌 쓰게 되고, 3단계로 늘릴 때 또 표가 하나 는다.

| 컬럼 | 뜻 |
|---|---|
| `name` | 화면과 모델에 나가는 이름. 같은 부모 아래에서 유일하다 |
| `sort_order` | 화면과 프롬프트에서의 순서 |
| `enabled` | 끄면 **새 분류에서 빠진다.** 이미 그 값으로 분류된 건은 그대로다 |
| `note` | 운영자 메모. 모델에 보내지 않는다 |

**지우지 않고 끈다.** 지우면 그 값으로 분류된 공고가 목록에 없는 값을 갖게 되고, 소비 측이
받는 값이 우리 목록 밖이 된다. 끄기는 되돌릴 수 있고 지우기는 아니다.

`normalized_jobs` 에 두 칸을 더한다.

| 칸 | 값 |
|---|---|
| `job_major` | 대분류 이름. 정하지 못하면 NULL |
| `job_minor` | 소분류 이름. 대분류만 정해지면 NULL |

**이름을 저장하고 id 를 저장하지 않는다.** `normalized_jobs` 는 재정규화로 다시 만들어지는
파생 표이고, 소비 측이 받는 것도 이름이다. id 를 넣으면 소비 측이 우리 표를 한 벌 더 갖게
된다. 이름이 바뀌면 다음 분류부터 새 이름이 붙는다.

## 2. 모델이 목록에서 고른다

`.claude/rules/llm.md` 가 정한 판정 칸의 모양을 그대로 따른다 — 닫힌 목록, 응답 스키마로
강제, 근거 문장, 근거가 본문에 없으면 버린다.

**다른 점은 목록이 코드가 아니라 표에서 온다는 것 하나다.** 응답 스키마의 `Literal` 을 호출
시점에 표를 읽어 만든다.

### 한 번에 부른다

**두 단계로 나누지 않는다.** 대분류를 먼저 고르고 그 안에서 소분류를 다시 묻는 방식은 호출이
두 배이고, 첫 판정이 틀리면 두 번째는 틀린 가지 안에서만 고른다.

전체 트리를 한 번에 보낸다. 씨앗 기준으로 이름 글자 합이 1,877자이고 구분자를 더해도 대략
3~4천 토큰이다. 지금 원문을 최대 12,000자 보내고 있으므로 늘어나는 양이 그보다 작고, 호출을
두 배로 만드는 것보다 싸다.

### 고르지 못하면 비운다

`판단불가` 를 목록에 둔다. 자리가 없으면 모델은 아무거나 고른다 (`app/classify/schema.py` 의
같은 판단). 판단불가는 저장할 때 NULL 이 된다.

**소분류만 못 고르는 경우가 있다.** `IT·개발` 인 것은 분명한데 `서버·백엔드` 인지
`웹풀스택` 인지 본문으로 갈리지 않는 공고가 그렇다. 그때는 대분류만 남기고 소분류를 비운다 —
찍어서 채우면 소비 측이 그것을 사실로 노출한다.

### 근거 검사

판정 칸이므로 값 자체가 원문에 글자로 있을 필요는 없다. `백엔드 개발자 채용` 어디에도
`IT·개발` 이라고 적혀 있지 않다. 대신 모델이 함께 낸 **근거 문장이 원문에 있는지** 본다
(`app/classify/grounding.py` 의 판정 칸 처리 그대로).

## 3. 어드민 화면

새 화면 하나. 네비게이션에 `직무 분류` 를 더한다.

| 구역 | 내용 |
|---|---|
| 목록 | 대분류와 그 아래 소분류. 켜짐·꺼짐, 그 값으로 분류된 공고 수 |
| 더하기·고치기 | 이름, 부모, 순서, 켜기·끄기, 메모 |
| 씨앗 넣기 | 표가 비어 있을 때만. `seeds/` 의 파일을 한 번에 넣는다 |

**공고 수를 함께 적는다.** 한 건도 안 붙은 소분류가 296개 중 몇인지 보이지 않으면 목록을
줄일 근거가 없다. 이름을 고칠 때는 **그 이름으로 이미 분류된 공고가 몇 건인지 알린다** —
고치면 그 건들의 값과 목록이 어긋난다.

## 4. 이미 쌓인 것

**아무것도 자동으로 돌지 않는다.** 표를 만들고 화면을 붙여도 기존 공고의 두 칸은 NULL 이다.

값을 채우려면 부가 워크플로우 화면에서 분류를 다시 건다. `all` 범위가 그 일이고, 640건이면
대략 285만 토큰이다 (`prd-side-workflows.md` 2절). **그것은 운영자가 건수를 보고 누르는
결정이지 이 PRD 가 자동으로 할 일이 아니다.**

## 개발 순서

| Push | 내용 | 검증 |
|---|---|---|
| 1 | `job_taxonomy` 표, 저장소 모듈, 씨앗 넣기 | 마이그레이션 적용·역적용, 씨앗 25/296 이 들어가는지 |
| 2 | `normalized_jobs` 에 두 칸, 분류 스키마를 표에서 만든다 | 표를 바꾸면 스키마가 따라오는지 |
| 3 | 프롬프트와 근거 검사. 대분류만 고른 경우 처리 | 픽스처로 판정과 버림 |
| 4 | 어드민 화면. 목록·더하기·고치기·끄기·공고 수 | 화면에서 만들고 끄고 확인 |
| 5 | 검수 화면과 계약 문서에 두 칸 | 화면 확인, 응답 키 대조 |

1~3 은 순서대로다. 4 는 1 뒤라면 언제든 된다.

## 끝났다고 말할 수 있는 조건

1. 어드민에서 직무를 더하고 고치고 끌 수 있고, 끈 값은 새 분류에 나오지 않는다
2. 분류가 표에 있는 값만 낸다. 표에 없는 값은 저장되지 않는다
3. 대분류만 정해진 공고는 소분류가 비어 있다. 찍어서 채우지 않는다
4. 근거 문장이 원문에 없으면 그 판정을 버리고 그 사실이 남는다
5. 이름을 고치면 그 이름으로 분류된 공고 수가 화면에 나온다
6. 검수 화면과 제공 API 에 두 칸이 나오고 계약 문서와 같다

## 열려 있는 것

**씨앗 296개 중 우리 사이트에 실제로 오는 것이 몇인가.** 재지 않았다. 분류를 한 번 돌려야
알 수 있고, 그 숫자가 목록을 줄이는 근거다.

**모델이 296개 중에서 실제로 고르는가.** 확인하지 못했다 — 2026-08-28 기준 Gemini 크레딧
고갈, Qwen 미결제, Claude·GPT 키 없음이라 실호출이 막혀 있다. 목록이 이만큼 길 때 판정이
쓸 만한지는 실측이 필요하고, 나쁘면 대분류를 먼저 좁히는 두 단계로 되돌릴 수 있다.

**`job_role` 과 겹치는가.** `job_role` 은 제목에서 그대로 뽑은 자유 텍스트이고 이 두 칸은
판정이다. 셋이 다 필요한지는 값이 쌓인 뒤에 본다.
