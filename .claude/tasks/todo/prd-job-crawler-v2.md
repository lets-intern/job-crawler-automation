# PRD: 크롤링 자동화 v2 — 목록 URL 하나로 등록하고, LLM 이 상세를 읽는다

> 작성일: 2026-08-24
> 대상 버전: v0.1.0 (`d5d61eb`) 이후
> 측정 근거: `.claude/docs/ocr-benchmark.md`

## 왜 바꾸나

지금은 크롤러를 등록할 때 운영자가 목록 URL 과 **상세 URL 을 같이** 넣어야 하고, 필드마다
셀렉터가 맞아야 한다. 두 가지가 걸린다.

**상세 URL 을 사람이 찾아 넣어야 한다.** 목록에서 상세로 가는 링크가 없는 사이트가 있고
(LG, 한화), 그때는 등록 자체가 막혔다.

**셀렉터는 등록된 필드만 준다.** 지금 4개다. 채용공고에는 조직 소개·주요 업무·필수 조건·우대
조건·전형 절차·고용 형태·근무지가 따로 있는데, 셀렉터로 13개를 맞추려면 사이트마다 13번
맞춰야 한다.

측정해 보니 둘 다 풀린다. **항목을 클릭하면 상세로 가고**, 상세 페이지의 텍스트를 LLM 에
넘기면 **13개 항목을 채운다.**

## 비목표

- **OCR 을 기본 경로로 쓰지 않는다.** 측정에서 화면을 캡처해 글자로 되돌리는 경로는 같은 공고의
  본문에서 글자를 틀렸다(`유해요인` -> `유해요일`, `산업안전보건법상` -> `산업안전보건법`).
  DOM 텍스트 경로는 원본과 일치했다. 캡처 경로는 **DOM 에 글자가 없는 공고에만** 남긴다
- 다중 사용자 권한 체계. 비밀번호 하나로 잠그는 지금 방식을 유지한다
- 로그인·CAPTCHA 우회. 그런 사이트는 범위 밖이다
- 분산 크롤링, 큐 서버, 두 번째 컨테이너

## 측정 결과 요약

같은 공고 하나(LG)를 처리하는 비용이다. 전문은 `.claude/docs/ocr-benchmark.md` 에 있다.

| 방식 | 초 | 토큰 | 이미지 저장 | 얻는 항목 |
|---|---|---|---|---|

| 렌더 HTML 통째로 LLM | 5.4 | 55,810 | 없음 | 13/13 |

## 무엇을 만드나

### 1. 목록 URL 하나로 등록한다

운영자가 넣는 것은 목록 URL 하나다. 상세 URL 을 묻지 않는다.

등록 과정이 스스로 한다.

1. 목록을 가져온다. 정적으로 반복 구조가 잡히면 정적, 아니면 렌더한다
2. 렌더하는 동안 오간 JSON·폼 응답을 같이 본다. **목록 API 가 있으면 그쪽이 우선이다**
3. API 가 없으면 반복 항목을 찾아 **첫 항목을 클릭한다.** 이동한 주소가 상세 URL 이고,
   그 주소 형식이 이후의 링크 규칙이 된다
4. 상세 페이지의 텍스트를 뽑아 LLM 에 넘겨 13개 항목을 받는다
5. 받은 값을 그 페이지에 다시 대조해 필드별로 채워졌는지 센다. 0건인 필드는 이름과 함께
   실패로 보인다

**클릭도 API 도 안 되면 등록을 실패시키고 이유를 말한다.** 상세 URL 을 손으로 넣는 길은
남긴다 — 지금 삼성이 그 경우다.

### 2. 새 탭과 이동 없음을 다룬다

SK 는 새 탭으로 열린다. 클릭 뒤 새 페이지가 열렸는지 보고, 열렸으면 그 페이지를 읽고 닫는다.

이동하지 않으면 **이동하지 않았다고 적는다.** 클릭했는데 아무 일도 없었던 것을 성공으로
넘기지 않는다.

### 3. 본문을 13개 항목으로 나눈다

상위 기업, 모집 기업, 조직 소개, 주요 업무, 필수 조건, 우대 조건, 전형 절차, 고용 형태,
근무지, 기타, 모집 시작일, 모집 마감일, 제목.

**있는 것만 채운다.** 화면에 없는 항목은 빈 값이고, 지어내지 않는다.

**LLM 이 읽은 원문 텍스트를 따로 저장한다.** 분류가 틀렸을 때 다시 볼 곳이 필요하다.
`raw_jobs` 가 그 자리이고 append-only 규칙은 그대로다.

분류와 정규화는 하는 일이 다르다. 분류는 "이 문단이 우대 조건이다" 를 정하고, 정규화는
"`2026.08.30 23:00` 을 `2026-08-30` 으로" 를 한다. **분류 뒤에 정규화 규칙이 돈다.**

### 4. 이미 저장한 공고는 상세를 열지 않는다

목록에서 아는 공고인지 먼저 가리고, 아는 공고는 클릭도 캡처도 LLM 호출도 하지 않는다.
비용이 새 공고에만 들게 하는 장치다.

**모집 기간이 끝난 공고는 목록에서 거른다.** 상세를 열지 않는다. 다만 날짜를 읽지 못한 항목은
진행 중으로 본다 — 못 읽은 것과 지난 것은 다르다. 건너뛴 수를 실행 기록에 남기고 실패와
구분해 보인다.

### 5. 단계를 나누고 상태로 관리한다

```
크롤러 생성 -> 테스트 -> 워크플로우 -> 텍스트 확보 -> 분류 -> 정규화 -> 검수
```

**단계마다 워크플로우를 만들지 않는다. 공고 한 건에 상태를 둔다.**

스케줄러가 하는 일은 목록 파싱과 텍스트 확보까지다. 그 뒤는 사람이 밀거나, 검수를 꺼두면
자동으로 흐른다.

사람 검수가 스케줄 실행을 막으면 안 된다. 30분마다 도는데 검수에서 사람을 기다리면 다음 실행이
겹치고, 지금 구현은 겹치면 건너뛰므로 크롤링이 조용히 멈춘다.

**검수 단계는 끄고 켤 수 있다.** 처음엔 켜서 품질을 보고 믿을 만해지면 끈다.

각 단계에서 실패하면 그 자리에 멈추고 사유를 남긴다. 재시도는 **그 단계만** 다시 한다.

### 6. 목록을 한꺼번에 등록한다

CSV 나 텍스트 입력으로 목록 URL 여러 개를 받아 순서대로 등록하고 테스트까지 돌린다.
운영자는 결과를 한 화면에서 확인하고 틀린 것만 고친다.

**한꺼번에 등록해도 사이트마다 딜레이는 그대로 지킨다.**

### 7. AI 제공자를 고른다

Claude, Qwen, Gemini, GPT 중에서 고른다. 고르는 자리는 둘이다 — 목록·크롤러 설정 쪽과
분류 쪽. AI 검수 단추에도 어느 것을 쓸지 정한다.

**이것은 `.claude/rules/llm.md` 와 충돌한다.** 그 파일에 "제공자는 Gemini 하나, 두 번째
제공자용 어댑터 층을 만들지 않는다" 가 명시돼 있다. **규칙을 먼저 고쳐야 한다.** 규칙을 두고
코드만 넣으면 다음에 또 충돌한다.

### 8. AI 호출을 기록하고 보여준다

호출마다 제공자·모델·기능·토큰·지연·비용을 남긴다. 별도 SQLite 파일에 쓴다 — 운영 DB 의
스냅샷 내보내기·가져오기가 로그 때문에 무거워지면 안 된다.

지금도 셀렉터 생성이 유일한 비싼 호출인데, v2 는 공고마다 분류 호출이 하나씩 붙는다.
숫자가 없으면 비용 질문에 답할 수 없다.

### 9. 운영 설정을 하위 메뉴로 정리한다

AI 토큰 설정, 동시 실행, 스냅샷, 데이터 가져오기를 하위 메뉴로 나눈다.

### 10. 화면을 정리한다

지금 산발적이라 알아보기 어렵다. Push 28 이 크롤러 등록·테스트·워크플로우·규칙·설정을 한 번
정리했다. v2 에서 늘어나는 화면도 같은 규칙을 따른다.

## 저장

**이미지는 저장하지 않는다.** 기본 경로가 텍스트라 이미지가 생기지 않는다. 캡처 경로를 쓰는
사이트에서만 파일로 남기고 DB 에는 경로만 둔다. 공고당 146~279KB 라 DB 에 넣으면 스냅샷
기능이 못 쓰게 된다.

**원문 텍스트는 저장한다.** 공고당 6KB 안팎이고 분류가 틀렸을 때 되돌릴 유일한 근거다.

## 열려 있는 것

- 삼성 상세 URL 형식. 목록 API 의 `a[data-value]` 가 공고 번호(`22,878` -> `22878`)인 것까지
  확인했고 상세 주소 형식은 아직 확인하지 않았다
- 제공자 4종의 실제 비용 비교. Gemini 만 측정했다
- 검수 3단계의 기본값. 처음부터 켤지 끌지
