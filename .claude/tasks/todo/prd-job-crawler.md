# 채용공고 크롤링 자동화 서비스 PRD

## 1. 개요

대기업 및 각 회사가 자체 채용 플랫폼에서 채용공고를 운영하기 때문에, 회사마다 크롤링 로직(파싱 셀렉터)을 매번 새로 구현해야 하는 반복 작업이 발생한다. 본 서비스는 **LLM을 이용해 CSS 셀렉터 생성을 자동화**하고, 검증된 셀렉터를 **워크플로우로 등록해 주기적으로 크롤링·정규화·적재**하는 내부 도구다.

이 웹 서비스는 최종 사용자용 채용공고 사이트가 아니라, **그 사이트에 데이터를 넘기기 전 단계의 크롤링 자동화 서버(백엔드 파이프라인)**다. 즉 이 서비스의 산출물은 정규화된 채용공고 데이터이며, 이후 별도의 채용공고 사이트가 이 데이터를 소비(조회/구독)하는 구조다.

## 2. 목표 / 비목표

**목표**
- 리스트 페이지 URL + 상세 페이지 URL만 입력하면 LLM이 CSS 셀렉터를 자동 생성
- 생성된 셀렉터를 테스트 실행으로 검증 후 워크플로우로 승격
- 워크플로우는 설정된 주기로 비동기 실행되며 신규 데이터만 DB에 적재
- 수집 데이터의 정규화 규칙을 웹에서 직접 수정 가능
- 수집 데이터를 웹 테이블로 조회

**비목표 (1차 범위 제외)**
- 다중 사용자 권한/인증 체계 (1차는 단일 운영자 가정)
- 대규모 분산 크롤링 (수백 개 이상 동시 워크플로우 스케일링)
- 로그인 필요/CAPTCHA 우회가 필요한 사이트 대응

## 3. 사용자 플로우

1. **셀렉터 생성**: 사용자가 웹에서 "채용 리스트 페이지 URL"과 "상세 페이지 URL"을 입력
2. 백엔드가 두 페이지의 HTML을 가져와 정제 후 LLM에 전달 → 리스트 항목(제목/링크/날짜 등)과 상세 항목(본문/자격요건 등) CSS 셀렉터를 JSON으로 생성
3. **테스트 실행**: "테스트" 버튼 클릭 → 생성된 셀렉터로 실제 크롤링 1회 실행 → 추출된 데이터 미리보기 표시
4. 결과가 정상이면 **"워크플로우에 넣기"** 버튼 클릭 → 워크플로우 이름 입력 → 워크플로우로 등록
5. **워크플로우 설정** 화면에서 크롤링 주기(예: 6시간마다) 설정
6. 등록된 워크플로우는 설정 주기에 따라 비동기로 실행되며, 신규 공고만 감지해 DB 적재
7. 워크플로우 목록 화면에서 각 워크플로우의 성공/실패 건수 확인, 실패율이 높으면 수동(또는 임계치 기반 자동) 중지
8. **데이터 정규화** 화면에서 필드 매핑/정제 규칙을 웹에서 수정 가능
9. **데이터 조회** 화면에서 수집된 채용공고를 테이블로 확인

## 4. 기능 명세

### 4.1 크롤러 등록 (셀렉터 생성)
- 입력: 리스트 페이지 URL, 상세 페이지 URL
- 처리: HTML 정제(스크립트/스타일 제거, 반복 리스트 아이템 샘플링) → LLM 호출 → CSS 셀렉터 JSON 생성
  - 리스트 페이지: 공고 아이템 selector, title, link(상세 URL 패턴), 날짜 등
  - 상세 페이지: 제목, 본문, 자격요건, 마감일, 부서 등
- 출력: 셀렉터 JSON을 화면에 표시, 편집 가능(자동 생성이 틀렸을 경우 수동 보정)

### 4.2 테스트 실행
- "테스트 실행" 버튼 → 저장된 셀렉터로 실제 페이지 재크롤링
- 결과: 추출된 필드별 데이터 미리보기 테이블 (성공/실패 항목 하이라이트)
- 실패 시 에러 사유(셀렉터 매칭 없음 등) 표시

### 4.3 워크플로우 등록/관리
- "워크플로우에 넣기" → 워크플로우 이름 입력 → 등록
- 워크플로우 목록 화면:
  - 이름, 대상 사이트, 크롤링 주기, 최근 실행 시각, 누적 성공/실패 건수
  - 실패 건수(또는 실패율)가 임계치 초과 시 알림 배지 표시 + 수동 중지 버튼
  - 필요 시 임계치 기반 자동 중지 옵션(설정 가능)
- 워크플로우 실행 방식: 스케줄러가 주기마다 비동기로 개별 워크플로우 실행, 실행 결과(성공 건수/신규 건수/실패 건수)를 로그로 기록

### 4.4 데이터 정규화
- 원본(raw) 크롤링 데이터와 정규화된 데이터를 분리 저장
- 정규화 규칙(필드 매핑, 텍스트 정제 패턴 등)을 웹 화면에서 등록/수정
- 규칙 변경 시 이후 신규 크롤링 데이터부터 적용 (기존 데이터 일괄 재정규화는 별도 버튼으로 지원 고려)

### 4.5 데이터 조회
- 수집된 채용공고를 테이블 뷰로 제공 (회사/워크플로우별 필터, 검색, 정렬)
- 상세 데이터(원문 링크 포함) 확인 가능

### 4.6 데이터 제공 (외부 연동)
- 정규화된 채용공고 데이터를 채용공고 사이트(별도 서비스)가 가져갈 수 있도록 제공
  - REST API로 조회 제공 (예: `GET /jobs?updated_after=...`) — 채용공고 사이트가 주기적으로 폴링해서 신규/변경 데이터를 가져가는 방식
  - 필요 시 웹훅 방식(신규 데이터 발생 시 콜백 URL로 push)도 고려 가능, 1차는 폴링 방식이 단순해서 우선 권장
- 연동 대상(채용공고 사이트)에서 이미 처리한 데이터인지 추적하기 위해 `normalized_jobs`에 전달 상태(예: `delivered_at`) 필드 필요

## 5. 데이터 모델 (SQLite, 초안)

```
crawlers
- id, name, list_url, detail_url, selectors_json, status, created_at

workflows
- id, crawler_id, name, interval_minutes, status(active/paused),
  success_count, fail_count, last_run_at, auto_stop_threshold

crawl_runs (실행 로그)
- id, workflow_id, started_at, finished_at, status, success_count, fail_count, error_message

raw_jobs (원본 수집 데이터)
- id, workflow_id, source_url, raw_data_json, crawled_at, hash(중복 감지용)

normalized_jobs (정규화된 데이터)
- id, raw_job_id, company, title, department, deadline, ..., normalized_at, delivered_at

normalization_rules
- id, field_name, rule_type(mapping/regex/trim 등), rule_config_json
```

## 6. 시스템 아키텍처

- **백엔드**: FastAPI 단일 서비스
  - API: 셀렉터 생성/테스트, 워크플로우 CRUD, 데이터 조회, 정규화 규칙 CRUD
  - **스케줄러**: 별도 Celery/Redis 없이 APScheduler로 워크플로우 주기 실행 (운영 단순화, 오버엔지니어링 방지). 워크플로우 수가 많아지면 추후 Celery로 교체 고려
- **크롤링 엔진**: Python 통일 권장 (FastAPI와 동일 스택 유지)
  - 정적 페이지: requests + BeautifulSoup
  - JS 렌더링 필요한 페이지: Playwright(Python)
  - Node를 별도로 두면 프로세스/배포가 두 스택으로 분리되어 운영 복잡도가 올라가므로, 1차는 Python 단일 스택 권장. Node가 꼭 필요한 사이트가 나오면 그때 별도 워커로 추가 검토
- **LLM 셀렉터 생성 모듈**: HTML 정제 → LLM API 호출(Anthropic API) → JSON 셀렉터 파싱/검증
- **DB**: SQLite (단일 파일, Docker 볼륨 마운트로 영속화)
- **프론트엔드**: HTMX + FastAPI 서버 사이드 렌더링(Jinja2 템플릿)
  - 별도 SPA 프레임워크/빌드 없이 FastAPI가 HTML 조각을 직접 렌더링하고 HTMX로 부분 갱신(테스트 실행 결과, 워크플로우 상태, 데이터 테이블 등)
  - 백엔드와 프론트가 같은 FastAPI 프로세스 안에서 동작하므로 Docker Compose 구성도 `api` 컨테이너 하나로 단순화 가능 (별도 `web` 컨테이너 불필요)

## 7. 배포

- Docker Compose 구성
  - `api` (FastAPI + APScheduler + HTMX 프론트엔드 렌더링, 크롤링 워커 포함) — 단일 컨테이너
  - SQLite 파일은 named volume으로 영속화
- 환경변수: LLM API 키, 크롤링 User-Agent, 기본 요청 간격(rate limit) 등

## 8. 비기능 요구사항

- 사이트별 robots.txt 확인 및 요청 간 딜레이 적용 (과도한 요청 방지)
- 크롤링 실패 시 재시도 로직(예: 3회 재시도 후 실패 처리)
- 셀렉터가 더 이상 매칭되지 않는 경우(사이트 구조 변경) 감지 → 실패 카운트 누적 → 임계치 초과 시 알림/중지
- 원본 HTML 스냅샷은 저장하지 않고 파싱 결과만 저장(저장소 절약), 단 셀렉터 실패 디버깅용으로 최근 실패 건 HTML은 임시 보관 고려

## 9. 미결정 사항 (Open Questions)

- 워크플로우 실행 동시성 제한 (동시에 몇 개까지 크롤링 실행할지)
- 정규화 규칙 변경 시 기존 데이터 일괄 재처리 여부/방식
- 인증/권한 필요 여부 (1차는 없음 가정)
- LLM 셀렉터 생성 실패(또는 저품질) 시 재시도/수동 개입 정책

## 10. 개발 환경 메모

- LLM API 키는 프로젝트 루트 `.env` 에 넣어 두었다. 현재 들어 있는 것은 **`GEMINI_API_KEY`** (Gemini) 하나다.
- `.env` 는 `.gitignore` 에 걸려 있어 커밋되지 않는다. 변수 이름은 `.env.example` 이 문서화한다.
- 6장의 셀렉터 생성 모듈은 Anthropic API 기준으로 적혀 있다. 실제 키가 Gemini 이므로 **어느 쪽으로 갈지 결정이 필요하다.** 결정되면 `.claude/rules/llm.md`, `.claude/docs/tech-stack.md`, `.env.example` 을 같이 고친다. (9장 미결정 사항에 추가)
