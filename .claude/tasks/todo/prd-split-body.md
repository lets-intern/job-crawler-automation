# PRD: 본문을 공통 항목으로 나눠 저장한다

> 작성일: 2026-08-25
> 기준: `main` `122ff3f` 이후
> 근거: 여섯 사이트 응답 실측 (`.claude/site-recipes/`, `tests/fixtures/`)

## 왜 바꾸나

지금 `normalized_jobs` 는 공고 하나를 여섯 칸에 담는다 — 회사·제목·부서·마감일·본문·자격요건.
그런데 **사이트가 이미 나눠서 주는 것을 우리가 도로 합치고 있다.**

| 사이트 | 응답에 나뉘어 오는 것 | 지금 |
|---|---|---|
| 한화 | `ruDtlJob`(직무내용), `rtExmQlf`(자격), `ruWorkpl`(근무지), `ruRcrtPrsn`(인원) | 셋을 `body` 로 이어붙임 |
| 현대 | `privJdDtl`(주요업무), `privMustReq`(필수), `prefReq`(우대), `aboutTeamNtc`(조직소개), `etc` | 셋을 `body` 로 이어붙임 |
| LG | `detailContext`, `requiredItem`, `preferredItem`, `recProcessInfo`, `locationName` | 일부만 씀 |
| 삼성 | `data.result` 41필드 | 일부만 씀 |

칸이 여섯인데 사이트가 여섯이라 안 맞는다. 빈 칸을 채우려다 **한화는 `부서` 에 근무지가 들어가
있고**(`ruWorkpl`), LG 는 조직명이 모집부문 수만큼 반복돼 `엔터프라이즈솔루션사업부
엔터프라이즈솔루션사업부` 가 된다. 307건 중 부서 43건, 자격요건 23건이 비어 있다.

**나누는 것이 토큰을 쓰지 않는다.** API 사이트 넷은 응답에 이미 있는 것을 매핑만 더 하면 된다.

## 목표

공고 하나가 사이트와 무관하게 같은 칸에 담긴다. 사이트가 주지 않는 칸은 **빈 값으로 둔다.**

## 비목표

- **LLM 분류.** 이 PRD 의 작업은 토큰을 쓰지 않는다. SK·롯데처럼 본문이 한 덩어리인 곳은
  `본문` 하나만 채우고 나머지를 비운다. 나눌지는 나중에 따로 정한다
- OCR, AI 제공자 넷 고르기, 호출 로그 DB — `.claude/tasks/memos/prd-crawler-v2-보류.md` 에 있다
- 다중 사용자 권한, 로그인·CAPTCHA 우회

## 공통 항목

여섯 사이트 응답을 대조해 뽑았다. **넷 이상에서 나오는 것만 칸으로 만든다** — 한 사이트만
가진 값을 칸으로 만들면 나머지 다섯이 비는 칸이 하나 는다.

넷이 주는데 지금 버리고 있다.

**`모집인원` 은 둘만 가지고 있어 칸으로 만들지 않는다.** 넷 이상 기준에 못 미친다.

## 억지로 채우지 않는다

**응답에 그 필드가 실제로 있을 때만 매핑하고, 없으면 비운다.**

지금 버그가 이것을 어겨서 생겼다 — 한화에 부서 개념이 없는데 빈 칸을 채우려고 근무지를 넣었다.
칸을 늘리면 6사이트 × 15칸 = 90번 이 판단을 하게 되고, 억지로 채우면 틀린 값이 그만큼 는다.

**빈 칸이 틀린 값보다 낫다.** 빈 칸은 "이 사이트는 이 값을 주지 않는다" 는 사실이고, 틀린 값은
소비 측이 그대로 노출한다.

## 본문 원문은 그대로 남는다

`raw_jobs` 는 append-only 라 수집한 원문이 이미 그대로 남는다. 추가 작업이 없다.

나눈 값이 틀린 것으로 판명되면 **재크롤링 없이** 매핑만 고쳐 다시 정규화한다. 정규화 규칙을
바꿀 때와 같다. 이것이 지금 나눠도 되는 이유다 — 되돌릴 수 있다.

`normalized_jobs.body` 는 나눈 뒤에도 남긴다. 덩어리로 오는 사이트(SK·롯데)에는 그것이 유일한
값이고, 나뉜 사이트에서도 원문을 한 자리에서 보는 값이 필요하다.

## 중복 값을 한 번만 적는다

`*` 로 배열을 훑으면 칸마다 값을 하나씩 얻는데, 그 값이 칸마다 같은 경우가 있다. 한화는 모집
부문이 셋이어도 근무지가 셋 다 `서울` 이라 `서울 서울 서울` 이 된다. 같은 값은 한 번만 적는다.
순서는 지킨다.

## 소비 측 계약

`.claude/docs/api-contract.md` 가 바뀐다. 칸이 늘어나므로 **더하는 방향이고 기존 칸은 그대로
둔다** — 소비 측이 읽던 것이 사라지지 않는다.

`normalized_at` 의 뜻은 바꾸지 않는다. 소비 측의 폴링 커서가 이 값에 걸려 있다.

전달된 행이 0건이라 지금은 바꿔도 소비 측에 영향이 없다. 붙기 전에 하는 것이 낫다.

## 끝났다고 말할 수 있는 조건

1. 여섯 사이트가 같은 칸 구조로 저장된다
2. 사이트가 주지 않는 칸은 비어 있고, **다른 값이 들어가 있지 않다**
3. 한화 `부서` 에 근무지가 없다
4. `서울 서울 서울` 같은 중복이 없다
5. 모집 시작일이 넷(LG·한화·삼성·SK)에서 채워진다
6. 제공 API 로 전량을 훑어 `제목`·`모집 기업`·`모집 마감일`·`본문 원문`·`원본 주소` 가 0건 비어 있다
7. 토큰을 쓰지 않는다

## 열려 있는 것

**상위 기업을 어디서 얻나.** 표에 크롤러 이름이라고 적었지만 크롤러 이름은 운영자가 쓴 글자다
(`LG`, `한화`). 이것을 그대로 쓸지, 크롤러에 칸을 따로 둘지 정해야 한다.

**SK·롯데의 덩어리를 언제 나눌지.** 이 PRD 는 나누지 않는다. 필요해지면 LLM 분류를 붙인다 —
공고당 약 4,453 토큰으로 측정돼 있다 (`.claude/docs/ocr-benchmark.md`).

**삼성 41필드 중 무엇을 쓸지.** `data.result` 에 필드가 41개인데 대조를 다 하지 않았다. 작업
때 확인한다.
