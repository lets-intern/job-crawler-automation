# PRD: 칸 구성을 바꾸고 회사 로고를 저장한다

> 작성일: 2026-08-28
> 기준 버전: v0.1.0-8-gc53d1ea
> 근거: `.claude/docs/api-contract.md`, `app/classify/schema.py`, `app/normalize/engine.py`,
> `seeds/site-configs-20260826.json`

## 목표

소비 측이 실제로 쓰는 칸만 남긴다. 칸 셋을 지우고, 직무를 더하고, 회사명을 모회사와 자회사로
가르고, 회사마다 로고 주소를 갖는다.

로고 파일은 MinIO 에 둔다. 엔드포인트를 어드민에서 바꿀 수 있게 해서 나중에 실제 S3 로
갈아끼운다.

## 지금 상태 (2026-08-28)

`normalized_jobs` 의 값 칸은 열여섯이다. 여섯은 수집이, 열하나는 분류가 채운다
(`app/normalize/engine.py`).

| 바꾸는 칸 | 지금 | 바뀐 뒤 |
|---|---|---|
| `department` 부서 | 분류가 뽑는 칸 | **지운다** |
| `job_category` 직군 | 분류가 고르는 닫힌 목록 15개 | **지운다** |
| `headcount` 모집인원 | 분류가 뽑는 칸 | **지운다** |
| `job_role` 직무 | 없다 | **더한다.** 제목에서 뽑는 자유 텍스트 |
| `company` 회사 | 파싱값과 크롤러 값을 하나로 합친 것 | 자회사 회사명. 없으면 비운다 |
| `parent_company` 모회사 | 없다 (`crawlers.default_company` 만 있다) | **더한다.** 크롤러 값 그대로 |

세 칸을 지우는 근거는 이미 있다. 2026-08-26 기록에 한화는 부서에 근무지가, SK 는 부서에
직무가, 네이버는 회사에 부서가 들어가 있었다
(`seeds/site-configs-20260826.json` 의 `why_the_mappings_were_removed`). 모집인원은 적지 않는
사이트가 많아 API 계약의 예시값이 `"0명"` 이다.

**세 칸 모두 제공 API 계약에 이름이 올라가 있다.** 소비 측은 아직 붙지 않았다
(`.claude/docs/api-contract.md`). 붙기 전에 바꾸는 것이 이 작업의 조건이다.

### 계약 문서가 스스로와 어긋나 있다

같은 문서가 같은 필드를 두 번 적었고 값이 다르다. 구현은 아래 표가 맞다.

| 위치 | employment_type | career_level |
|---|---|---|
| 83번째 줄 | 정규직 / 인턴 / 기간제 | 신입 / 경력 |
| 107번째 줄 | 정규직 / 계약직 / 인턴 / 기타 | 신입 / 경력 / 무관 |

같은 것을 표와 산문으로 두 번 적지 않는다 (`.claude/rules/writing.md`). 한쪽을 지운다.

## 비목표

- **태그.** 2026-08-28 에 범위에서 뺐다. 다시 꺼낼 때 직군이 있던 자리가 비어 있다는 것만
  적어 둔다 — 직무는 자유 텍스트라 소비 측이 그것으로 거를 수 없다
- **로고를 사이트에서 긁는 것.** 운영자가 올린다. 남의 이미지를 수집해 우리 저장소에 두는 것은
  이 서비스가 하는 일이 아니다
- 회사 정보를 더 담는 것(업종, 규모, 소개). 로고 주소 하나다
- 이미 쌓인 행의 지워진 칸 값을 살려 두는 것. 재정규화가 다시 만든다
- 실제 AWS S3 에 붙이는 것. 어드민에서 엔드포인트를 바꾸면 되는 상태까지다

## 1. 칸 셋을 지운다

`department`, `job_category`, `headcount` 를 지운다. 지우는 자리가 다섯 군데다.

| 자리 | 무엇 |
|---|---|
| `normalized_jobs` | 컬럼 셋 |
| `app/normalize/rules.py` | `NORMALIZED_FIELDS` |
| `app/classify/schema.py` | `JUDGE_FIELDS` 에서 `job_category`, `EXTRACT_FIELDS` 에서 둘 |
| `app/api/review_filter.py` | `FIELD_LABELS`, `EMPTY_NOTES` |
| `.claude/docs/api-contract.md` | 필드 표 |

`raw_jobs` 는 건드리지 않는다. 셀렉터가 뽑아 둔 값은 그대로 남고, 정규화가 그것을 읽지 않게
될 뿐이다 (`.claude/rules/data-safety.md`).

`job_classifications` 의 지난 값도 지우지 않는다. 표는 그대로 두고 읽지 않는다 — 지우면
칸 구성을 되돌릴 때 640건을 다시 분류해야 한다.

## 2. 직무를 더한다

`job_role`. **제목에서 뽑는 자유 텍스트**다. 닫힌 목록이 아니다.

뽑는 칸이므로 지금 여덟 칸과 같은 규칙을 받는다 — 있는 글자를 그대로 옮기고, 없으면 빈
문자열이고, 옮긴 값을 원문에서 찾지 못하면 버린다 (`app/classify/grounding.py`).

**근거 검사의 대상에 제목을 더한다.** 지금은 본문에만 돌려 보는데, 직무는 제목에서 오는 값이라
본문에만 돌리면 맞게 뽑은 값이 통째로 버려진다.

## 3. 회사명을 모회사와 자회사로 가른다

지금은 파싱값이 있으면 그것을, 없으면 `crawlers.default_company` 를, 그것도 없으면 크롤러
이름을 써서 **하나의 `company` 에 합친다**. 합치기를 그만둔다.

| 칸 | 값 | 채우는 쪽 |
|---|---|---|
| `parent_company` | 크롤러의 `default_company`, 없으면 크롤러 이름 | 정규화. 크롤러 값 그대로 |
| `company` | 공고에서 파싱한 회사명. 없으면 NULL | 수집 |

**모회사는 LLM 이 판정하지 않는다.** 크롤러에 적힌 값을 그대로 옮긴다. 본문을 읽어 정하게
두면 삼성 사이트 공고에 모회사가 다른 이름으로 나오는 사고가 난다.

**자회사가 없으면 비운다.** 모회사 이름으로 채우지 않는다 — 채우면 계열사가 실제로 갈리는
공고와 그렇지 않은 공고를 소비 측이 구분할 수 없다. 삼성 채용 사이트 하나에 삼성SDS 와
삼성전기가 섞여 들어오고, 그 둘을 가르는 것이 이 칸의 존재 이유다.

`company_source` 는 지운다. 두 칸으로 갈린 뒤에는 어느 출처인지가 칸 이름으로 드러난다.

## 4. 회사 표를 만든다

로고는 공고 단위가 아니라 회사 단위 값이다. `normalized_jobs` 에 넣으면 같은 주소가 100건에
100번 복사된다.

```
companies
  id, name, parent_name, logo_url, created_at, updated_at
```

`name` 은 유일하다. **정규화가 처음 보는 회사명을 만나면 행을 만든다.** 로고는 비어 있고,
운영자가 화면에서 채운다. 자동으로 만들지 않으면 운영자가 회사명을 손으로 다시 타이핑하게 되고,
그러면 오타 하나로 로고가 안 붙는다.

행을 자동으로 지우지는 않는다. 공고가 다 사라진 회사의 로고를 지우는 것은 운영자가 한다.

로고는 회사명으로 잇는다. 한 번 등록하면 그 회사명을 가진 공고 전부에 붙고, 공고마다
따로 넣는 동작은 만들지 않는다. 그래서 등록 화면이 할 일은 하나다 — **로고가 없으면서
공고가 여러 개인 회사를 앞에 세우는 것.** 공고 한 건짜리를 먼저 등록하느라 백 건짜리가
뒤에 서면 그 화면은 일을 늘리기만 한다.

## 5. MinIO 를 붙인다

**이것은 두 번째 컨테이너다.** `.claude/rules/core.md` 가 들이지 말라고 한 것 중 하나이고,
2026-08-28 에 예외로 결정했다. 파일 저장은 SQLite 한 파일로 할 수 없는 일이고, S3 호환이라
나중에 실제 S3 로 엔드포인트만 바꿔 옮길 수 있다. **규칙 파일에 이 예외와 근거를 적는다.**

`.claude/rules/crawling.md` 도 고친다. 지금 "우리가 운영하는 서비스는 `app/notify/` 하나뿐이고
그것만 공유 fetch 클라이언트를 건너뛴다"고 적혀 있는데, 저장소가 두 번째가 된다.

### 설정

MinIO 는 S3 API 를 그대로 말한다. 그래서 붙는 쪽 코드는 하나이고, **엔드포인트를 바꾸는 것이
곧 저장소를 바꾸는 것**이다. 다만 한 칸만 바꿔서 되지는 않는다 — 아래 여섯이 한 벌이다.

| 키 | 값 | MinIO | AWS S3 |
|---|---|---|---|
| `s3_endpoint` | 서버가 부르는 주소 | `http://minio:9000` | 비운다. SDK 가 지역으로 만든다 |
| `s3_region` | 지역 | 무시된다. `us-east-1` 로 둔다 | 실제 지역이어야 한다 |
| `s3_bucket` | 버킷 이름 | | |
| `s3_access_key` | 접근 키 | | 다른 값이다 |
| `s3_secret_key` | 비밀 키 | | 다른 값이다 |
| `s3_public_base` | 브라우저가 이미지를 읽는 공개 주소 | | 엔드포인트와 다르다 |

주소 형식은 SDK 가 알아서 고르게 둔다. MinIO 는 `엔드포인트/버킷/키` 로, S3 는
`버킷.s3.지역.amazonaws.com/키` 로 부르는데, 엔드포인트가 비어 있으면 SDK 가 뒤쪽을 쓴다.
운영자가 고를 값이 아니다.

`app_settings` 에 넣는다. 새 표를 만들지 않는다 (`app/notify/settings.py` 와 같은 방식).

**키가 스냅샷에 딸려 나간다.** LLM 키가 이미 그렇고 내보내기 화면이 그 사실을 알린다
(2026-08-27 결정, `app/api/import_data.py` 의 `_merge_llm_settings`). 같은 방식으로 가되
**내보내기 화면의 경고에 이 키를 더한다.** 경고에 없는 비밀은 없는 것으로 읽힌다.

### 바꾼 뒤에 확인한다

저장하면 **연결 확인** 단추로 실제 왕복을 한 번 한다. 작은 객체를 넣고, 읽고, 지운다. 넷 중
어디서 실패했는지를 문장으로 적는다 — 키가 틀린 것과 버킷이 없는 것과 주소에 못 닿는 것은
고치는 방법이 다르다.

**확인은 저장된 값으로 한다.** 폼에 적힌 값이 아니라 다음 업로드가 실제로 쓸 값이라야 확인이
뜻을 갖는다. 순서는 저장하고 나서 확인이다 (`app/api/ui_notify.py` 의 테스트 전송과 같다).

### 바꿔도 이미 올린 파일은 따라가지 않는다

엔드포인트를 바꾸면 **다음 업로드부터** 그쪽으로 간다. `companies.logo_url` 에 이미 적힌
주소는 옛 저장소를 가리킨 채로 남는다. 파일을 옮기는 동작은 만들지 않는다 — 회사가 열몇
곳이라 옮기는 것을 만드는 비용이 다시 올리는 비용보다 크다.

**화면에 그 사실을 적는다.** 회사 목록에서 로고 주소가 지금 설정의 `s3_public_base` 로
시작하지 않는 행을 `옛 저장소` 로 표시해, 무엇을 다시 올려야 하는지 눈으로 보이게 한다.

### 올리는 길

운영자가 회사 화면에서 이미지 파일을 고르면 서버가 MinIO 에 넣고 `companies.logo_url` 에
공개 주소를 적는다. 이미 어딘가에 올려 둔 주소를 그대로 붙여넣는 길도 둔다.

받는 것은 이미지뿐이고 크기 상한을 둔다. 형식과 상한은 화면에 적는다.

### docker-compose

`docker-compose.yml` 에 MinIO 서비스와 볼륨을 더한다. 운영 배포(`docker-compose.coolify.yml`)에
어떻게 넣을지는 로컬이 도는 것을 본 뒤에 정한다.

|---|---|
| 데이터 검수 | 열 셋이 사라지고 직무·모회사가 는다. 스물셋에서 스물둘이 된다 |

## 개발 순서

| Push | 내용 | 검증 |
|---|---|---|
| 1 | 칸 셋 삭제. 마이그레이션, `NORMALIZED_FIELDS`, 분류 스키마, 라벨, 계약 문서 | 재정규화 후 남은 칸이 그대로인지 |
| 2 | 직무를 더한다. 뽑는 칸으로, 근거 검사에 제목을 더한다 | 픽스처로 제목에서 뽑히는지 |
| 3 | 회사명을 두 칸으로 가른다. `company_source` 삭제 | 계열사가 섞인 사이트 픽스처로 |
| 4 | `companies` 표와 자동 등록 | 처음 보는 회사명에 행이 생기는지 |
| 5 | 저장소 설정과 MinIO 연동. docker-compose | 로컬에서 올리고 주소로 읽히는지 |
| 6 | 회사 화면. 로고 올리기와 붙여넣기 | 화면에서 올려 확인 |
| 7 | 검수 화면 열 정리, 내보내기 경고 문구 | 화면 확인 |

1~3 은 순서대로다. 4~6 은 1~3 과 서로 기다리지 않는다.

## 끝났다고 말할 수 있는 조건

1. `normalized_jobs` 에 `department`·`job_category`·`headcount` 가 없고, 재정규화가 남은 칸을
   그대로 만든다
2. 직무가 제목에서 뽑히고, 제목에만 있는 값이 근거 검사에서 버려지지 않는다
3. 계열사가 섞인 사이트에서 모회사와 자회사가 각각 다른 값으로 나온다. 자회사가 없는 공고는
   자회사가 비어 있다
4. 처음 보는 회사명이 들어오면 `companies` 에 행이 생기고 로고는 비어 있다
5. 화면에서 로고를 올리면 MinIO 에 들어가고, 저장된 주소로 이미지가 열린다
6. 어드민에서 엔드포인트를 바꾸면 다음 업로드가 그쪽으로 간다
7. 내보내기 화면의 경고가 저장소 키를 함께 적고 있다
8. `.claude/docs/api-contract.md` 가 스스로와 어긋나지 않고, 실제 나가는 값과 같다

## 열려 있는 것

**운영 배포에 MinIO 를 어떻게 넣을 것인가.** Coolify 다. 로컬이 도는 것을 본 뒤에 정한다.

**로고 파일 형식과 크기 상한.** 정하지 않았다. Push 5 에서 정한다.

**같은 회사가 사이트마다 다른 이름으로 들어올 때.** `삼성전기` 와 `삼성전기(주)` 가 두 행이
된다. 이름을 맞추는 것은 `mapping` 규칙의 일이지만, 규칙을 고친 뒤 이미 생긴 행을 어떻게
합칠지는 정하지 않았다.

**직무를 제목에서만 뽑을 것인가.** 제목에 없고 본문에만 있는 공고가 얼마나 되는지 재지 않았다.
Push 2 에서 픽스처로 본다.
