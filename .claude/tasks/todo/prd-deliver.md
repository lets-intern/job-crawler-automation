# PRD: 소비 측에 실제로 전달한다

> 작성일: 2026-08-25
> 기준: `main` `122ff3f` 이후
> 근거: 운영 DB 실측 (`normalized_jobs` 314건, `delivered_at` 0건)

## 왜 이것이 다음인가

이 서비스의 존재 이유는 정규화된 공고를 채용공고 사이트에 주는 것이다
(`.claude/rules/core.md`). 그런데 **한 번도 준 적이 없다.**

| | |
|---|---|
| 쌓인 공고 | 314건 |
| 전달된 공고 | **0건** |

수집·정규화·화면·알림·배포까지 만들었는데 **정작 출력이 한 번도 쓰인 적이 없다.** 계약이 실제로
도는지, 커서가 누락 없이 넘어가는지, `delivered_at` 이 제대로 찍히는지 아무도 모른다.

그리고 붙이려면 먼저 정해야 하는 것이 계약 문서에 미정으로 남아 있다.

> **소비 측에 자격증명을 어떻게 줄지는 아직 정하지 않았다.** (`.claude/docs/api-contract.md`)

다른 후보들과 견줘 이것을 골랐다. `prd-split-body.md` 는 아무도 받지 않는 데이터를 더 잘게
나누는 일이고, 자동 등록은 받는 곳이 없는 데이터를 더 모으는 일이다. **받는 쪽이 없으면 둘 다
값이 나지 않는다.**

## 목표

채용공고 사이트가 **오늘 붙일 수 있는 상태**로 만든다. 그쪽 코드가 아직 없어도 참조 소비자로
계약이 도는 것을 증명한다.

## 비목표

- 채용공고 사이트 자체를 만드는 것. 그것은 별도 서비스다
- 본문을 나누는 것 (`prd-split-body.md`)
- 새 사이트 등록

## 1. 자격증명은 소비 측 전용 토큰으로 한다

지금 `/api/jobs` 는 운영 화면과 같은 비밀번호 쿠키로 잠겨 있다. 소비 측에 그것을 주면 안 된다.

**화면 비밀번호를 주면 크롤러를 지우고 DB 를 통째로 내려받을 수 있다.** 읽기만 하면 되는 쪽에
운영 권한을 같이 주는 셈이다.

**소비 측은 사람이 아니라 프로그램이다.** 로그인 화면에 비밀번호를 넣고 쿠키를 받는 흐름은
서버끼리 주고받는 데 맞지 않는다.

그래서 이렇게 한다.

- 환경변수로 받는 토큰 하나. `Authorization: Bearer <토큰>` 헤더로 온다
- 이 토큰은 **`/api/jobs` 와 `/api/jobs/delivered` 만** 연다. 화면도 운영 API 도 열지 않는다
- 운영자의 화면 쿠키로도 여전히 열린다. 사람이 브라우저에서 확인할 수 있어야 한다
- 토큰이 설정되지 않았으면 **소비 측 접근은 닫힌 채로 둔다.** 기본값으로 열지 않는다 —
  `ADMIN_PASSWORD` 의 기본값 `1234` 에서 겪은 것과 같은 실수를 반복하지 않는다
- 값을 로그·응답·화면에 남기지 않는다

## 2. 참조 소비자를 만든다

채용공고 사이트가 아직 없어도 계약이 도는 것을 증명해야 한다. **저장소 안에 참조 소비자를
둔다.** 그쪽 개발자가 그대로 베껴 쓸 수 있는 것이어야 한다.

하는 일은 셋이다.

1. 커서를 끝까지 넘기며 공고를 전부 받는다
2. 받은 것의 id 를 모아 `POST /api/jobs/delivered` 로 알린다
3. 다음에 다시 돌면 **이미 받은 것은 오지 않고 새 것만** 온다

이것은 시험 도구가 아니라 **계약의 실행 가능한 설명**이다. 문서의 예제가 낡는 것과 달리 이것은
테스트가 돌린다.

## 3. 계약을 확정한다

`.claude/docs/api-contract.md` 의 미정 항목을 지운다. 남길 것은 이것들이다.

- 인증 방법과 토큰을 어디서 받는지
- 커서를 어떻게 이어 받는지, 끝났다는 것을 어떻게 아는지
- `delivered_at` 을 언제 찍고 그것이 무엇을 뜻하는지
- 소비 측이 데이터를 잃었을 때 되받는 법 (`updated_after`)
- 한 번에 몇 건까지 받을 수 있는지

**문서에 적는 주소·필드명은 코드에서 복사한다.** 기억으로 다시 쓰지 않는다.

## 4. 되받을 수 있어야 한다

소비 측이 데이터를 잃거나 처음부터 다시 받아야 할 때가 온다. `updated_after` 로 그 시점부터
다시 받는 길이 이미 있다. **그것이 실제로 도는지 확인하고 문서에 적는다.**

`delivered_at` 이 찍혀 있어도 `updated_after` 로는 다시 받을 수 있어야 한다 — 그 값은 "보낸 적
있다" 는 기록이지 "다시는 못 받는다" 가 아니다.

## 5. 재정규화가 전달 기록을 지우지 않는다

`normalized_jobs` 를 다시 쓸 때 `delivered_at` 이 살아남아야 한다. 지워지면 소비 측이 이미 받은
공고를 전부 다시 받는다.

규칙에는 적혀 있다 (`.claude/rules/data-safety.md`). **아직 증명된 적이 없다.** 재정규화를 돌려
전달 기록이 그대로인지 확인한다.

## 끝났다고 말할 수 있는 조건

1. 토큰 하나로 `/api/jobs` 를 받고 `/api/jobs/delivered` 를 찍을 수 있다
2. 그 토큰으로 **화면과 운영 API 는 열리지 않는다**
3. 토큰이 없으면 소비 측 접근이 닫혀 있다
4. 참조 소비자가 314건을 **누락도 중복도 없이** 받는다
5. 두 번째로 돌리면 **0건**이 온다. 새 공고가 들어오면 그것만 온다
6. 재정규화를 돌려도 `delivered_at` 이 그대로다
7. `updated_after` 로 이미 전달한 것을 다시 받을 수 있다
8. 계약 문서에 미정 항목이 없다

## 열려 있는 것

**토큰을 어떻게 건네고 어떻게 바꾸나.** 환경변수로 넣는 것까지는 정했다. 유출됐을 때 바꾸는
절차(양쪽을 동시에 바꿔야 한다)를 문서에 적을지 정해야 한다.

**한 번에 몇 건까지 줄지.** 지금 상한이 얼마인지 확인하고, 314건이 몇 번에 나뉘는지 재서
문서에 적는다.
