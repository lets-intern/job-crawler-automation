## 왜 이 Push 가 생겼나

사용자가 화면에서 직접 겪은 두 가지다.

크롤러를 만들 수는 있는데 지울 수 없었다. `DELETE /api/crawlers/{id}` 가 아예 없었다.

한화 등록은 502, 현대자동차 등록은 201 이었다. 근본 원인은 둘 다 정적 HTML 에 목록이 없는 것인데
응답이 갈렸다. 현대는 LLM 이 빈 `<ul id="applyList">` 컨테이너를 보고 `#applyList li` 를 찍었고,
목록 4개 필드가 전부 0개 매칭인데도 저장됐다.

## 삭제 동작

| 상황 | 응답 |
|---|---|
| 워크플로우 행이 있음 | 409 `has_workflow`. 해당 워크플로우 번호와 먼저 지우라는 안내 |
| 행은 없고 상태만 `promoted` | 409 `promoted` |
| 없는 크롤러 | 404 |
| `draft` 또는 `tested` | 삭제 |

함께 지우는 것은 `crawl_runs` 에서 `crawler_id = ? AND workflow_id IS NULL` 인 행뿐이다.
승격 전 테스트 실행 기록이고, 이 크롤러 하나만 가리키므로 정의가 사라지면 읽을 수 없다.

`raw_jobs` 와 `normalized_jobs` 는 지우지 않는다. 이 둘은 워크플로우에 매달려 있고 워크플로우가
있는 크롤러는 삭제 자체가 거절되므로 지워질 경로가 없다. 두 테스트로 못 박았다 — 거절된 삭제 후
행 수 불변, 다른 크롤러를 지워도 행 수 불변.

## 판정 일관성

목록 필드가 전부 0개 매칭이면 422 로 거절하고 `crawlers` 행을 만들지 않는다.

판정은 `list.` 로 시작하고 `skipped` 가 아닌 필드가 전부 `failed` 일 때만 참이다.
응답이 없다고 한 선택 필드(`list.company`)는 빠지고, 상세가 다 잡혀도 목록이 없으면 거절된다.

일부만 실패하면 지금대로 201 로 저장하고 `failed_fields` 에 이름을 싣는다. 사람이 손으로 고칠 수
있어야 한다 (`.claude/rules/llm.md`).

실패 메시지가 다음 행동을 알린다.

> 정적 HTML 에서 목록을 찾지 못했다. 목록 필드 list.item, list.title, list.link, list.date 가
> 모두 0개 매칭이다. JS 로 목록을 그리는 사이트일 수 있으니 렌더 모드 승격을 검토한다

502 가 아니라 422 인 근거는, 모델은 답을 제대로 냈고 사이트가 정적 HTML 로 목록을 주지 않는
것이기 때문이다. 업스트림 실패를 뜻하는 502 와 다르다.

**하지 않았다.** Push 9 가 `app/templates/` 를 커밋 없이 고치는 중이었고, 확인 시점에 수정된
템플릿이 12개였다. 그중 셋이 삭제 버튼이 들어갈 바로 그 파일이었다. 8분 폴링했으나 대상이

Push 9 완료 후 처리해야 한다.

화면의 **등록 실패 표시는 이미 동작한다.** 등록 라우트가 예외를 잡아 `reason`·`message` 를 결과
영역에 적으므로 현대자동차 같은 케이스는 템플릿 수정 없이 사유가 화면에 나온다.
