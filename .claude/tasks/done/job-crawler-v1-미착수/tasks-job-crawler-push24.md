## 배경

지금은 운영자가 모드를 손으로 고른다. 여섯 사이트 중 넷이 정적으로는 안 나오고, LG 는 API 가
있다는 것을 사람이 F12 로 찾아야 했다. 그 확인을 등록 과정이 대신한다.

판정에 필요한 관찰은 **렌더 한 번**에 다 나온다. 페이지를 렌더하면서 오간 JSON 응답을 같이
보면 정적으로 되는지, API 가 있는지, 브라우저가 꼭 필요한지가 한 번에 갈린다.

## 관련 파일

- `app/selector/generator.py` - 지금의 셀렉터 생성. 판정 결과를 받아 어느 쪽을 만들지 정한다
- `app/crawler/playwright.py` - 렌더 중 응답을 관찰하는 자리
- `app/crawler/fetcher.py` - 정적 시도
- `.claude/rules/llm.md` - 모델은 제안자다. 낸 것은 반드시 그 자리에서 돌려 본다

        - 렌더는 어차피 한 번 한다. 그 동안 오간 응답 중 JSON 만 모은다
        - 후보는 "dict 의 배열을 담고 있고 그 길이가 렌더된 항목 수와 비슷한 것" 이다.
          길이가 맞는 것이 여럿이면 긴 쪽부터 본다

        - [ ] 24.2.V 검증: 저장한 LG 응답 픽스처로 `data.jobNoticeList` 를 후보로 집어내는지.
              후보가 없는 픽스처에서는 빈 결과가 나오는지
    - [ ] 24.3 후보 JSON 의 필드 매핑을 모델에게 맡기고, 그 자리에서 검증한다

        - 응답은 매핑 스키마로 제약하고, 받은 매핑을 **실제 응답에 그대로 돌려** 필드별로 몇 개가
          채워지는지 센다. 0건인 필드는 실패로 이름과 함께 남긴다
        - 매핑이 실패하면 `api` 로 올리지 않는다. `playwright` 로 떨어뜨린다
        - 잘못된 응답에 한해 한 번만 다시 시도한다
        - [ ] 24.3.V 검증: 저장한 LG 응답으로 생성 호출, 필드별 매칭 개수 확인

        - 무엇을 보고 그 모드를 골랐는지 사람이 읽을 문장으로 크롤러에 저장한다.
