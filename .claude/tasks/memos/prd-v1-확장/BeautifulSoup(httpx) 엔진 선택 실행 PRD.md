
# [확장] BeautifulSoup(httpx) 엔진 선택 실행 PRD

> 본 문서는 `job-crawler-prd.md`(채용공고 크롤링 자동화 서비스)의 확장 기능이다. 1차 PRD에서 "Playwright 단일 엔진"으로 결정했던 부분을 확장해, **정적 사이트는 BeautifulSoup(httpx) 엔진을 선택해서 실행**할 수 있게 한다.

## 1. 개요

Playwright는 JS 렌더링이 필요한 사이트엔 필수지만, 정적 HTML 사이트에도 무조건 브라우저를 띄우면 리소스(메모리 200~400MB/실행, CPU 렌더링 부하)를 불필요하게 소모한다. httpx + BeautifulSoup은 브라우저 프로세스 없이 HTTP 요청·HTML 파싱만으로 동작해 리소스 소모가 훨씬 적고, 동시 실행 가능한 워크플로우 수도 크게 늘어난다.

이 확장은 **크롤러 등록 시 엔진을 선택**할 수 있게 하여, 정적 사이트는 가벼운 BeautifulSoup으로, JS 렌더링이 필요한 사이트는 기존 Playwright로 각각 처리하도록 한다.

## 2. 목표 / 비목표

**목표**
- 크롤러 등록 화면에서 엔진(Playwright / BeautifulSoup)을 선택 가능하게 함
- 선택한 엔진으로 셀렉터 생성 → 테스트 실행 → 워크플로우 실행까지 일관되게 동작
- BeautifulSoup 엔진 사용 시 서버 리소스가 아닌 **대상 사이트에 대한 예의(rate limit)**가 실질적 제약이 되므로, 사이트별 동시성/요청 간격 설정을 지원
- 기존 크롤러의 엔진을 나중에 변경 가능하게 함 (셀렉터 재검증 필요)

**비목표**
- 엔진 자동 판별(정적/동적 여부를 시스템이 알아서 감지해 선택) — 1차는 사용자가 수동으로 선택. 자동 판별은 Open Question으로 이관
- 사이트별 프록시/IP 로테이션 등 우회 기법 — 범위 밖

## 3. 사용자 플로우

1. 크롤러 등록 화면(리스트 URL, 상세 URL 입력)에서 **엔진 선택** (기본값: Playwright, 유지)
   - "BeautifulSoup (가벼움, 정적 사이트 전용)" / "Playwright (JS 렌더링 지원)" 중 선택
2. 선택한 엔진으로 페이지를 가져와 LLM이 셀렉터 생성
   - BeautifulSoup 선택 시, 서버는 JS 렌더링 없이 fetch한 원본 HTML을 기준으로 셀렉터를 생성 → 만약 채용공고 데이터가 HTML에 없으면(JS로 렌더링되는 구조) 화면에 "이 사이트는 정적 HTML에 데이터가 없어 보입니다. Playwright로 전환해보세요" 안내
3. "테스트 실행" 버튼 클릭 시 선택된 엔진으로 실제 크롤링 → 결과 미리보기 (기존과 동일한 흐름)
4. 결과가 정상이면 워크플로우로 등록, 이후 워크플로우 실행도 저장된 엔진 값 그대로 사용
5. 기존 크롤러의 엔진을 변경하고 싶으면 크롤러 설정에서 엔진 변경 → 테스트 재실행으로 재검증 필요 (변경 즉시 워크플로우에 반영되지 않고, 재검증 통과 후 반영)

## 4. 기능 명세

### 4.1 엔진 선택 UI
- 크롤러 등록/수정 화면에 엔진 선택 필드 추가 (라디오 버튼 또는 드롭다운)
- 엔진 설명을 짧게 노출: BeautifulSoup은 "정적 HTML 전용, 가벼움" / Playwright는 "JS 렌더링 지원, 무거움"
- 워크플로우 목록/상세 화면에도 각 워크플로우가 어떤 엔진을 쓰는지 표시

### 4.2 셀렉터 생성 (엔진별 분기)
- BeautifulSoup 선택 시: `httpx.AsyncClient`로 HTML fetch → LLM에 정제된 HTML 전달 → CSS 셀렉터 생성
- Playwright 선택 시: 기존 로직 그대로 (브라우저 렌더링 후 HTML 확보)
- 두 엔진 모두 결과 스키마(셀렉터 JSON)는 동일한 포맷 유지 — 이후 실행 로직에서 엔진만 다르고 파싱 방식은 공통

### 4.3 테스트 실행 / 워크플로우 실행
- 저장된 `engine` 값에 따라 실행 시점에 사용할 클라이언트(httpx vs Playwright)를 분기
- BeautifulSoup 엔진 크롤러는 브라우저 컨텍스트를 아예 생성하지 않으므로, Playwright 동시성 세마포어와 별도의 **BeautifulSoup 전용 동시성 제한**을 둠 (서버 자원보다 대상 사이트 부담이 제약이므로, 사이트별로 낮게 설정 가능해야 함)

### 4.4 사이트별 요청 정책 (신규)
- 크롤러별로 다음 설정 추가:
  - `request_delay_ms`: 같은 사이트에 대한 요청 간 최소 간격 (기본값 예: 1000ms)
  - `max_concurrency`: 해당 사이트에 대한 동시 요청 수 (기본값 예: 1~2)
- 이 설정은 BeautifulSoup 엔진에서 특히 중요 (자원 여유가 크다고 무분별하게 동시 요청을 늘리면 대상 사이트에 부담을 주거나 IP 차단당할 수 있음)
- Playwright 엔진에도 동일 필드 적용 가능하게 하여 두 엔진에서 일관된 정책 관리

### 4.5 엔진 변경
- 기존 크롤러의 엔진을 변경할 수 있는 UI 제공
- 변경 시 자동으로 워크플로우에 반영되지 않고, "테스트 재실행 → 정상 확인 → 반영" 절차를 다시 거치도록 함 (엔진이 바뀌면 셀렉터가 안 맞을 수 있으므로 검증 필수)

## 5. 데이터 모델 변경 (기존 PRD 확장)

```
crawlers 테이블에 컬럼 추가
- engine (playwright / beautifulsoup, 기본값 playwright)
- request_delay_ms (기본값 1000)
- max_concurrency (기본값 1)
```

## 6. 비기능 요구사항

- BeautifulSoup 엔진이라도 robots.txt 확인 절차는 동일하게 적용
- 요청 실패(타임아웃, 4xx/5xx) 시 재시도 로직은 기존 정책(예: 3회 재시도) 재사용
- 사이트별 동시성/딜레이 설정이 없는 크롤러는 보수적인 기본값(딜레이 1초, 동시성 1)으로 시작해 문제 없으면 사용자가 직접 조정하도록 안내
- httpx 커넥션 풀은 프로세스 전역에서 재사용해 매 요청마다 커넥션을 새로 맺지 않도록 함

## 7. 미결정 사항 (Open Questions)

- 엔진 자동 판별(먼저 httpx로 시도, 데이터 없으면 Playwright로 자동 재시도 후 추천) 기능을 추후 추가할지
- 사이트별 동시성/딜레이 값을 어드민에서 어떤 단위(사이트별/워크플로우별)로 관리할지, 기본값을 얼마로 둘지
- robots.txt에서 명시적으로 금지된 경우 크롤러 등록 자체를 막을지, 경고만 표시할지
- BeautifulSoup 엔진에서 JS 렌더링 여부를 사전에 판별해 사용자에게 엔진 추천을 해줄 수 있는지 (예: 초기 HTML과 렌더링 후 HTML을 비교해 차이가 크면 Playwright 권장)
