# [확장] 페이지네이션 크롤링 PRD

> 본 문서는 `job-crawler-prd.md`(채용공고 크롤링 자동화 서비스)의 확장 기능이다. 기존 셀렉터 생성/크롤링 로직이 리스트 페이지의 첫 페이지만 대상으로 했던 부분을, 여러 페이지(및 무한스크롤/더보기)까지 따라가며 수집하도록 확장한다.

## 1. 개요

채용공고 리스트는 보통 여러 페이지로 나뉘어 있거나(쿼리 파라미터/다음 버튼) 무한스크롤·더보기 버튼으로 이어진다. 첫 페이지만 크롤링하면:
- 워크플로우를 처음 등록하는 시점(DB가 비어있는 상태)에 과거 공고를 충분히 확보하지 못함
- 크롤링 주기 사이에 신규 공고가 첫 페이지 노출 개수보다 많이 올라오면 일부를 놓침

이를 해결하기 위해 셀렉터 생성 단계에서 페이지네이션 방식을 함께 판별하고, 크롤링 실행 시 **"이미 수집한 공고를 만나면 정지"**하는 방식으로 여러 페이지를 순회하되 불필요한 과다 크롤링은 피하도록 한다.

## 2. 목표 / 비목표

**목표**
- 셀렉터 생성 시 페이지네이션 방식(쿼리 파라미터형 / 다음 버튼형 / 무한스크롤·더보기형 / 없음)을 함께 판별해 저장
- 워크플로우 실행 시 리스트가 최신순 정렬이라는 전제하에, 이미 DB에 있는 공고를 만나면 그 지점에서 페이지 순회를 중단(중복 감지 기반 정지)
- 최초 실행(DB가 비어있는 백필 상황)과 이후 정기 실행 모두 동일한 로직으로 자연스럽게 커버
- 무한루프/과다 크롤링을 막는 안전장치(`max_pages`) 적용

**비목표**
- 리스트 정렬이 최신순이 아닌 사이트에 대한 별도 대응 (1차는 최신순 정렬을 전제로 함, 아닌 경우는 Open Question)
- 페이지네이션 없이 전체 페이지를 강제로 끝까지 도는 옵션 (필요성이 확인되면 추후 검토)

## 3. 사용자 플로우

1. 크롤러 등록 시 리스트 페이지 URL을 넣으면, 셀렉터 생성 과정에서 LLM이 리스트 아이템 셀렉터와 함께 **페이지네이션 방식**도 함께 판별해 결과에 포함
2. 테스트 실행 시 페이지네이션 방식에 따라 실제로 다음 페이지(또는 다음 스크롤/더보기)까지 1~2회 시도해보고 정상 동작하는지 미리보기로 확인
3. 워크플로우 실행 시:
   - 페이지 1부터 순차적으로 수집
   - 각 공고를 만날 때마다 중복 여부(기존 raw_jobs의 dedup hash와 비교) 확인
   - 이미 존재하는 공고를 만나는 순간, 그 페이지까지만 처리하고 다음 페이지로 넘어가지 않음
   - 최초 실행(DB에 해당 크롤러의 데이터가 없음)일 때는 자연히 `max_pages`까지(또는 페이지네이션이 끝날 때까지) 순회하며 백필

## 4. 기능 명세

### 4.1 페이지네이션 방식 판별 (셀렉터 생성 단계)
LLM이 리스트 페이지 셀렉터와 함께 아래 정보를 JSON으로 반환:
```json
{
  "pagination": {
    "type": "query_param" | "next_button" | "infinite_scroll" | "none",
    "url_pattern": "https://.../jobs?page={n}",   // query_param인 경우
    "next_selector": ".pagination .next",           // next_button인 경우
    "load_more_selector": ".btn-load-more",         // infinite_scroll/더보기인 경우
    "max_pages": 10
  }
}
```
- `query_param`: URL의 페이지 번호를 1씩 증가시키며 요청
- `next_button`: Playwright로 "다음" 버튼 클릭 → 목록 갱신 대기 → 반복
- `infinite_scroll`: 스크롤 또는 "더보기" 버튼 클릭을 반복하며 새 항목 로드
- `none`: 페이지네이션 없음, 단일 페이지만 존재

### 4.2 중복 감지 기반 정지 로직
- 각 공고 항목에 대해 dedup hash(제목+링크 등 조합)를 계산해 기존 `raw_jobs`에 이미 존재하는지 확인
- **정지 조건**: 한 페이지 내에서 이미 존재하는 공고를 하나 이상 만나면, 해당 페이지까지 처리 후 다음 페이지로 진행하지 않고 종료
  - 리스트가 최신순 정렬이라는 전제이므로, 기존 공고를 만났다는 것은 그 이후는 이미 수집된 데이터라는 뜻
- 신규 워크플로우(첫 실행, 기존 데이터 없음)는 이 조건에 걸리지 않으므로 자연스럽게 `max_pages` 상한까지 백필 수집
- 정기 실행에서는 대부분 신규 공고가 적어 1~2페이지 내에서 조기 종료됨

### 4.3 안전장치
- `max_pages` 상한 도달 시 강제 종료 (사이트가 정렬을 지키지 않거나 판별 오류가 있어도 무한 크롤링 방지)
- 같은 페이지를 반복해서 가져오는 경우(다음 버튼/무한스크롤이 실제로는 진행되지 않는 경우) 감지해 종료 — 직전 페이지와 결과가 완전히 동일하면 중단
- 페이지 이동 중 실패(타임아웃 등) 시 그 지점까지 수집한 데이터는 유지하고 실패로 기록 (기존 재시도 정책 재사용)

## 5. 데이터 모델 변경 (기존 PRD 확장)

```
crawlers 테이블에 컬럼 추가
- pagination_config_json (type, url_pattern/next_selector/load_more_selector, max_pages)
```

## 6. 비기능 요구사항

- 페이지 이동 간에도 기존 요청 정책(request_delay_ms, max_concurrency)을 동일하게 적용해 대상 사이트에 과도한 부담을 주지 않음
- dedup hash 조회는 페이지 순회마다 반복되므로, 크롤러 단위로 인덱싱해 조회 성능 저하 방지

## 7. 미결정 사항 (Open Questions)

- 리스트가 최신순 정렬이 아닌 사이트(예: 인기순, 마감임박순)에 대한 처리 방식 — 정지 조건이 성립하지 않으므로 별도 전략 필요 (예: 항상 `max_pages`까지 순회 후 신규만 필터링)
- 백필 시 `max_pages`를 워크플로우별로 다르게 설정할 수 있게 할지 (공고가 매우 많은 대기업 사이트 대응)
- 무한스크롤 사이트에서 "새 항목이 로드되지 않음"을 판별하는 구체적 기준(대기 시간, DOM 변화 감지 방식)
