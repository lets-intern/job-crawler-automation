# Tasks: 수집은 최소한, 나누는 것은 LLM

> PRD: `.claude/tasks/memos/보류/llm-classify/prd-llm-classify.md`
> 브랜치: `feat/auto-register`
> 상태: 진행 중

## 배경 (PRD 를 안 봐도 되도록)

칸마다 사이트별 매핑을 적는 방식을 해봤고 **절반도 못 채웠다.** 502건 실측이다.

```
제목·본문·원본주소 100%   회사명 98%   마감일 71%   시작일 70%
나머지 열세 칸        21~66%
```

판단이 사이트 11곳 × 칸 16개 = **176번**이었고 그중 다섯 곳에서 뜻이 다른 칸에 값이 들어가
있었다. 사이트가 하나 늘 때마다 16번이 더 는다.

**수집은 여섯 칸만 하고, 나누는 것은 LLM 이 본문을 읽고 한다.**

```
수집:  title · body · start_date · deadline · company · source_url
분류:  body -> job_category work_location career_level employment_type
              headcount duties preferred hiring_process requirements
              department etc_info
```

칸은 이미 있다 (마이그레이션 0011·0012 적용됨). 새로 만들지 않는다.

## 1.1 결과 (2026-08-26)

셀렉터를 `blockquote:has(strong:-soup-contains("모집 기간"))` 으로 좁혔다. 인용문을 마감일로
읽던 것이 사라졌다.

정규화 규칙 셋도 같이 고쳤다 — 머리말 패턴에 공백과 글머리표를 허용(`모집 기간 • `), 꼬리말
제거 규칙 추가(`자정까지`), 두 자리 연도 형식 추가(`%y년 %m월 %d일`). 운영 DB 의 마감일 원문
280가지에 태워 **되살아나는 것 1개, 망가지는 것 0개**를 확인하고 넣었다.

토스 264건을 지우고 다시 받았다. 600초 제한에 걸려 두 번에 나눠 돌았다.

| | 전 | 후 |
|---|---|---|
| `raw_jobs` | 640 | 640 |
| `normalized_jobs` | **502** | **640** |
| 토스 정규화 | 126 / 264 | **264 / 264** |
| 토스 마감일 | 0 | 1 |

마감일이 1건인 것이 맞는 답이다. 토스는 대부분의 공고에 마감일을 적지 않는다 — 264건 중 본문에
`모집 기간` 글자가 있는 것이 4건이다. 인용문을 잡던 시절에는 8건이 "채워졌는데" 그중 7건이
틀린 값이었다.

## 1.8 결과 — 표본 스무 건 (2026-08-26)

열한 사이트에서 골고루 스무 건을 골라 실제로 분류했다. 사이트를 돌아가며 한 건씩 집고, 같은
실행에서 연달아 들어온 건만 보지 않도록 사이트 안에서도 벌려서 골랐다.

**지어낸 값이 소비 측으로 나간 것은 0건이다.** 살아남은 값은 전부 근거가 본문에 있다.
모델이 세 번 지어냈고(LG 두 건의 `duties`, 그중 한 건의 `department`) 검증이 전부 걸러냈다.

### 첫 시도는 스무 건 모두 실패했다

`response_schema` 의 enum 에 빈 문자열을 넣었더니 Gemini 가 400 으로 거절했다
(`response_schema.properties[career_level].enum[0]: cannot be empty`). 본문을 보내기 전에
막혀서 **토큰은 나가지 않았고**, `raw_jobs` 도 `normalized_jobs` 도 그대로였고, 실패한 호출
스무 건이 `llm_calls` 에 `ok=0` 으로 남았다. 분류 실패가 수집을 건드리지 않는다는 것이 실제로
확인된 셈이다.

고친 방법은 빈 문자열 대신 `판단불가` 를 목록에 넣는 것이다. 저장될 때는 빈 칸이 되고,
`tests/test_classify_body.py` 가 enum 에 빈 값이 다시 들어오는 것을 막는다.

### 칸별 채움률 — 매핑 방식과 견주면

640건 매핑 방식의 숫자와 표본 20건의 숫자다. 표본이 스무 건이라 오차가 크다.

| 칸 | 매핑 방식 (640건) | 분류 (표본 20건) |
|---|---|---|
| 직군 | 53% | **95%** |
| 자격요건 | 65% | 70% |
| 기타 | 66% | **95%** |
| 근무지 | 65% | **25%** |
| 주요업무 | 63% | **85%** |
| 전형절차 | 63% | 65% |
| 경력 | 45% | **75%** |
| 우대사항 | 39% | **65%** |
| 모집인원 | 37% | 30% |
| 고용형태 | 26% | 40% |
| 조직·부서 | 21% | **70%** |

**근무지가 65% 에서 25% 로 떨어졌다.** 매핑 방식에서는 사이트가 별도 필드로 주던 값이고,
본문에는 근무지가 글자로 안 적힌 공고가 많다. 이 칸은 수집으로 되돌릴지 판단이 필요하다.

### etc_info 에 무엇이 쌓이는가

스무 건 중 열아홉 건에 값이 있다. 길이는 최소 93자, 중앙 326자, 최대 2,585자다.

| 종류 | 열아홉 건 중 |
|---|---|
| 지원 방법·접수 (온라인 접수, 채용 홈페이지) | 13 |
| 문의처 (1:1 문의, Q&A 게시판, FAQ) | 9 |
| 허위기재·합격취소 유의 | 8 |
| 전형 일정·결과 발표 안내 | 7 |
| 근무조건·처우 (직급, 내규, 근무제도) | 6 |
| 보훈·장애인 우대 등 법정 문구 | 5 |
| 병역·해외여행 결격 | 4 |
| 조직 소개 | 1 |

한 건에 여러 종류가 섞인다. 개인정보 처리 문구와 자격증·어학 문구는 0건이었다.

덩어리가 크게 셋으로 갈린다. **어느 공고에나 붙는 상투 문구**(지원 방법, 문의처, 허위기재,
법정 우대), **그 공고에만 있는 안내**(전형 일정, 처우, 근무제도), 그리고 **어느 칸에도 안
맞는 서술**(조직 소개, 회사 소개 — 7·18 삼성이 그렇다).

판단은 하지 않는다. 칸을 더 만들지 합칠지는 이 표를 보고 정한다.

### 칸끼리 겹치는가

**값이 통째로 겹치는 쌍은 없었다.** 두 칸의 값이 같거나 한쪽이 다른 쪽에 통째로 들어간
경우를 스무 건 전부에서 찾았고 0건이다.

다만 **판정 칸의 근거가 다른 칸 안에 들어 있는 경우**는 흔하다. 같은 문장을 근거로도 쓰고
값으로도 담는다는 뜻이다.

| 판정 칸 | 근거 문장이 들어 있던 칸 |
|---|---|
| 직군 | 주요업무 5건, 자격요건 3건, 기타 1건, 조직·부서 1건 |
| 경력 | **자격요건 7건**, 기타 2건 |
| 고용형태 | 고용형태 자신 3건, 기타 2건 |

`경력` 은 스무 건 중 일곱 건에서 자격요건 문장을 근거로 삼았다 (`5년 이상 경험이 있으신 분`).
겹친다기보다 **자격요건에서 읽어 낸 요약이 경력 칸**이라는 관계다.

### 스무 건에서 0건인 칸

없다. 열한 칸 모두 한 번 이상 채워졌다.

## 1.9 전에 정해야 할 것 — 옛 값이 분류를 이긴다

**이것이 지금 열려 있는 유일한 문제다.**

정규화는 규칙(수집이 준 값)을 분류보다 먼저 둔다. 그런데 `raw_jobs` 는 append-only 라
2026-08-26 이전에 수집된 640건에는 옛 매핑이 넣어 둔 값이 그대로 남아 있다. 그래서 그
행들은 분류를 돌려도 옛 값이 이긴다.

표본에서 실제로 그랬다.

| 공고 | `raw_jobs` 의 옛 값 | 분류가 고른 값 | `normalized_jobs` 에 남은 값 |
|---|---|---|---|
| SK 808 | `제조 - 설비관리(기계)` / `Permanent` / `Experienced` | 생산·제조 / - / 경력 | **옛 값 그대로** |
| LG 911 | `경영지원\n\n침해사고 예방 및 대응` | 개발·IT | **옛 값 그대로** |
| 네이버 1145 | `'\n     \t\n   '` (공백만) | 연구개발 | **옛 값 그대로** |
| 토스 1419 | 없음 | 기타 / 정규직 / 경력 | 분류 값 |

옛 값이 남아 있는 건수는 `job_category` 269, `employment_type` 131, `career_level` 230 이다.
그래서 **닫힌 목록이 640건에 대해서는 성립하지 않는다.** 소비 측이 직군으로 거르려면
`개발·IT` 와 `IT - 구축/운영/최적화` 와 `경영지원\n\n침해사고 예방 및 대응` 을 다 알아야 한다.
`.claude/docs/api-contract.md` 에 이 예외를 적어 두었다.

### 사용자가 3번을 골랐다 (2026-08-26)

**뽑는 칸까지 포함해 분류가 전부 이긴다.** 1.2 가 수집을 여섯 칸으로 줄여서 사이트가 그 열한
칸을 아예 주지 않는다 — LG·한화의 수집 필드는 `body` `company` `deadline` `start_date`
`title` 뿐이다. 그러면 분류가 그 열한 칸의 유일한 출처다. 새 규칙이 아니라 이미 정한 규칙을
기존 데이터에도 적용하는 것이다.

빈 칸까지 덮는다. 채워진 칸만 덮으면 분류가 `판단불가` 를 낸 자리에 옛 값이 남고, 그 순간
닫힌 목록이 640건에 성립하지 않는다.

**수집이 주는 여섯 칸은 분류가 건드리지 않는다** — `title` `body` `company` `deadline`
`start_date` `source_url`. `deadline` 은 마감 지난 공고 건너뛰기가 걸려 있고, `company` 는
계열사 구분이라 본문에서 못 뽑는다 (348건 중 32%만 본문에 회사명이 있다).

구현은 `app/normalize/engine.py` 의 `apply_classification()` 한 곳이다. `.claude/docs/api-contract.md`
의 "옛 값 예외" 절과 `.claude/docs/data-model.md` 의 우선순위 문단을 같은 커밋에서 고쳤다.

## 분류 기준을 둘로 나눴다 (2026-08-26, 사용자 지시)

"본문에 글자로 있어야 한다" 는 기준이 열한 칸 전부에 걸려 있었다. 그 기준으로는 직군을 영원히
채울 수 없다 — `백엔드 개발자 채용` 어디에도 "직군: 개발" 이라고 적혀 있지 않다.

| | 칸 | 근거를 무엇으로 보나 |
|---|---|---|
| 뽑는 칸 | `duties` `requirements` `preferred` `hiring_process` `work_location` `headcount` `department` `etc_info` | 값 자체가 본문에 있어야 한다 |
| 판정 칸 | `job_category` `employment_type` `career_level` | 닫힌 목록 안이어야 하고, 근거 문장이 본문에 있어야 한다 |

판정 칸은 목록을 **응답 스키마의 enum 으로 강제**한다. 프롬프트로만 부탁하면 "지킵니다" 가
아니라 "대개 지킵니다" 가 되고, 대개는 640건에서 스무 건쯤 어긋난다는 뜻이다.

판정 칸마다 근거 문장(`*_evidence`)이 함께 온다. 그 문장이 본문에 없으면 판정을 버린다 —
읽고 고른 것인지 지어낸 것인지 가를 방법이 그것뿐이다. 근거는 `job_classifications.evidence_json`
에 남는다 (마이그레이션 0015).

### 목록은 어디서 왔나

운영 DB 640건의 지금 값을 세어서 뽑았다. 지어내지 않았다.

`career_level` — **신입 / 경력 / 무관**

지금 값은 `경력` 100, `Experienced` 77, `Irrelevant` 15, `신입/경력` 15, `New` 11, `신입` 8,
`인턴` 2, `무관` 2 로 230건이다. 같은 뜻이 사이트마다 다른 낱말로 쌓여 있다. `Experienced` 는
`경력`, `New` 는 `신입` 이다. `Irrelevant` 와 `신입/경력` 은 둘 다 "어느 쪽이든 지원할 수
있다" 라 `무관` 하나로 모았다 — 갈라 두면 소비 측이 "신입 지원 가능" 을 세 값으로 물어야
한다. `인턴` 2건은 경력 구분이 아니라 고용형태라 여기 두지 않았다.

`employment_type` — **정규직 / 계약직 / 인턴 / 기타**

지금 값은 `Permanent` 71, `계약` 35, `어시스턴트` 9, `정규직` 7, `인턴` 3, `정규` 3,
`기간제` 2, `계약 / 육아휴직 대체 채용(정규 전환 가능)` 1 로 131건이다. `Permanent`·`정규`
는 `정규직` 이고 `계약`·`기간제` 는 `계약직` 이다. `어시스턴트` 는 카카오 한 곳의 낱말이라
칸으로 만들지 않고 `기타` 가 받는다.

`job_category` — **개발·IT / 연구개발 / 생산·제조 / 품질·안전 / 건설·플랜트 / 영업 /
마케팅 / 기획·전략 / 경영지원 / 재무·회계 / 법무 / 구매·물류 / 디자인 / 고객서비스 / 기타**

지금 값은 269건에 **170가지가 넘는다.** `IT - 구축/운영/최적화`, `Tech R&D - 설계`,
`일반직\n\n생산/제조` 처럼 사이트마다 제 분류 체계를 그대로 싣고 있어서 소비 측이 이 칸으로
거를 수 없다. 그래서 값의 앞머리(`X - Y` 의 `X`, 줄바꿈 앞)를 세어 묶었다:

`IT서비스` 35, `Tech R&D` 20, `연구/개발` 17, `일반직` 16, `제조` 13, `건설/플랜트` 13,
`IT` 13, `서비스비즈` 11, `경영지원` 10, `생산/품질` 9, `영업` 7, `법무` 7, `고객서비스` 7,
`영업/마케팅` 6, `안전보건` 5, `Infra` 5, `연구직` 4, `재무` 3, `정보보안` 2,
`사무/행정지원` 2, `전략기획` 2, `구매` 1, `사업개발` 1, `기업문화` 1, `마케팅` 1 ...

`디자인` 은 지금 값의 앞머리에는 없지만 640건의 제목·본문에 61건이 걸린다. 나머지 열넷은
전부 위 셈에서 왔다. `교육`(1건)과 `의료`(17건, 대부분 복리후생 문구)는 신호가 약해 넣지
않았다 — 목록에 있는데 아무도 안 고르는 값은 모델을 헷갈리게만 한다.

어디에도 맞지 않으면 `기타` 이고, 본문만으로 판단할 수 없으면 빈 칸이다.

## 1.9 결과 — 400 / 640 에서 크레딧이 떨어졌다 (2026-08-26)

**Gemini 선불 크레딧이 소진돼 240건이 남았다.** 420번째 호출부터 전부 같은 429 다.

```
Gemini 호출 실패(429): Your prepayment credits are depleted.
```

키를 채우면 그대로 이어 돌면 된다. 건마다 저장 즉시 커밋되고 `pending_ids()` 가 남은 것만
집어 들어서, 다시 걸면 240건부터 시작한다. 지금까지 쓴 토큰은 다시 쓰지 않는다.

남은 240건은 **전부 토스**다. 1.1 에서 재수집한 264건이 id 뒤쪽에 몰려 있고 분류가 id 순으로
돌았기 때문이다. 그 264건은 이미 여섯 칸 설정으로 다시 받은 것이라 옛 매핑 값이 없다 —
그래서 아직 분류가 안 됐는데도 닫힌 목록은 640건 전부에서 성립한다 (아래).

### 실행

|---|---|
| 대상 | 640건 |

### 1.9.V — 칸별 채움률, 제공 API 640건 전량

`GET /api/jobs` 를 커서로 네 장 넘겨 640건을 받았다. 읽기만 했고 `delivered_at` 은 그대로다.

같이 내려간다** — 늘어난 138건이 대부분 마감일 없는 토스 공고다. 수집 칸의 `-15` 는 수집이

**근무지와 모집인원이 크게 내렸다.** 둘 다 매핑 방식에서는 사이트가 별도 필드로 주던 값이고,
본문에는 글자로 안 적힌 공고가 많다. 표본 20건에서 근무지 25%·모집인원 30% 였고 400건에서
35%·12% 다. 이 두 칸은 수집으로 되돌릴지 판단이 필요하다 — 1.9 가 끝난 뒤에 볼 일이다.

### 되돌리는 법

분류를 걸기 전 DB 사본이 볼륨 안에 있다.

```
/data/jobs-before-classify-all-20260826.db
```

되돌리려면 그 파일을 `/data/jobs.db` 로 되돌리면 된다. 스키마 변경은 없었다 —
마이그레이션을 돌리지 않았고 `job_classifications` 행과 `normalized_jobs` 의 열한 칸만
바뀌었다. `raw_jobs` 와 `delivered_at` 은 손대지 않았다.

## 하지 않는 것

- 새 칸을 만드는 것. 열한 칸으로 나누고 나머지는 `etc_info` 다
- AI 제공자 넷 고르기. 지금은 Gemini 하나다
- 소비 측 전달. 사용자가 자기 방식으로 한다
