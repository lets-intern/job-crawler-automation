## 여기서 멈췄다

2026-08-26, 3.4 를 세는 중에 사용자가 방향을 바꿨다. **수집은 최소한만 하고 나누는 것은 LLM
이 한다.** 크롤링으로 받는 것은 제목·본문·모집시작일·모집마감일·회사명·원본주소까지고, 본문을
공통 항목으로 나누는 일은 LLM 이 맡고 남는 것은 기타로 간다.

그래서 이 Push 의 남은 항목(3.4 대조 · 3.5 · 3.6)은 **하지 않는다.** 사이트마다 셀렉터로
열여섯 칸을 나눠 담는다는 전제 자체가 바뀌었고, 그 전제 위에서 매핑이 맞는지 대조하는 것은
지금 헛일이다.

**Push 1·2 가 더한 칸 열 개는 지우지 않는다.** LLM 분류가 채울 자리가 된다. `start_date` 는
그대로 수집으로 채운다.

### 이어받는 사람이 알아야 할 운영 상태

멈춘 시점의 DB 와 설정은 이렇게 두었다. **셋 다 사람이 되돌려야 한다.**

| 무엇 | 지금 | 원래 | 되돌리는 자리 |
|---|---|---|---|
| ntfy 알림 | 꺼짐 | 켜짐 | 운영 설정 화면의 알림 켜기 |
| 워크플로우 열한 개 | 전부 `paused` | 여섯 개가 `active`, 다섯 개는 없었음 | 워크플로우 화면의 재개 |
| 스케줄러 잡 | 0개 | 여섯 개 | 위를 되돌리면 따라온다 |

`paused` 로 둔 것은 지금은 오히려 맞다 — 매핑이 바뀌는 중에 주기 실행이 옛 설정으로 계속
받으면 그것도 헛일이다. 새 방향의 수집 설정이 정해진 뒤에 되돌린다.

데이터는 비웠고 다시 채웠다. `raw_jobs` 640건, `normalized_jobs` 502건이다. 비우기 직전
백업이 스크래치패드의 `jobs-before-purge-20260826.db` 에 있다 (321건 시점).

## 배경

전부 비어 있다. `source_url` 이 같아 재수집으로 덮이지도 않는다.

사용자가 **비우고 다시 받기로 결정했다** (2026-08-26).

        **이 두 표가 방향을 바꾼 근거다.** 제목과 본문은 100%, 회사명 98% 인데 나머지 열세
        칸은 21~71% 다. 사이트마다 셀렉터로 나눠 담는 방식으로는 여기가 천장이다.
    - [ ] 3.5 알림을 다시 켜고 주기 실행을 확인한다 — **하지 않는다.** 위 "여기서 멈췄다"
        - [ ] 3.5.V 검증: 주기 실행이 한 번 도는 것을 기다려 `trigger=schedule` 행과
              신규 0·건너뜀 전건을 확인한다
    - [ ] 3.6 화면과 계약 문서를 맞춘다 — **하지 않는다.** 위 "여기서 멈췄다"
        - 데이터 검수 화면이 새 칸을 보이고 고칠 수 있게 한다
        - `.claude/docs/api-contract.md` 와 `data-model.md` 에 새 칸을 적는다.
          **더하는 방향이고 기존 칸은 그대로 둔다**
        - [ ] 3.6.V 검증: 화면을 열어 새 칸이 보이고 수정이 저장되는지. 문서의 필드명과 코드 대조

        읽기만 해 본 결과 3.6 은 Push 2 가 이미 해 두었다. `app/api/review.py` 의 조회가 열여섯
        칸을 읽고, `app/api/review_filter.py` 의 `FIELD_LABELS` 와 `EMPTY_NOTES` 에 새 칸 열
        개가 있고, `migrations/0012` 와 `app/normalize/engine.py` 의 `OVERRIDABLE_FIELDS` 가
        열여섯 칸으로 넓혀져 있다. `.claude/docs/api-contract.md` 와 `data-model.md` 에도 새
        칸이 적혀 있다. **화면을 실제로 열어 저장까지 해 보지는 않았다** — 그래서 체크하지
        않는다.
