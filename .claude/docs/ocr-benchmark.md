# 수집 방식 네 가지 실측 (2026-08-24)

수집을 OCR 로 바꾸기 전에, 같은 상세 페이지에 네 방식을 돌려 시간과 토큰을 쟀다.
저장소 코드는 고치지 않았고 스크래치패드의 별도 스크립트로 측정했다.

## 무엇을 쟀나

| 방식 | 하는 일 |
|---|---|
| 1. 정적 파싱 | httpx 로 HTML 을 받아 셀렉터로 뽑는다 |
| 2. 렌더 파싱 | Playwright 로 렌더한 뒤 같은 셀렉터로 뽑는다 |
| 3. OCR 텍스트만 | 캡처해서 모델에 넘겨 글자만 받는다 |
| 4. OCR + 분류 | 캡처해서 글자를 받고, 13개 항목으로 나눈 결과도 받는다 |

모델은 `gemini-3.5-flash-lite`. 캡처는 1280px 폭, 전체 페이지, JPEG 품질 75.
셀렉터는 DB 에 저장된 것을 그대로 읽어 썼다.

대상은 두 곳이다. 정적으로 되는 곳과 안 되는 곳을 같이 봐야 비교가 성립한다.

- 롯데: `https://recruit.lotte.co.kr/apply/announcement/detail/21931885`
- LG: `https://careers.lg.com/apply/detail?id=1002099` (SPA)

## 결과

### 롯데 (정적으로 되는 곳)

| 방식 | 초 | 입력 토큰 | 출력 토큰 | 필드 수집 |
|---|---|---|---|---|
| 1. 정적 파싱 | 0.18 | 0 | 0 | 4/4 |
| 2. 렌더 파싱 | 5.17 | 0 | 0 | 4/4 |
| 3. OCR 텍스트만 | 8.84 | 1,137 | 920 | 글자 1,460자 |
| 4. OCR + 분류 | 10.62 | 2,294 | 1,330 | 4/4, 13개 항목 중 12개 채움 |

### LG (SPA)

| 방식 | 초 | 입력 토큰 | 출력 토큰 | 필드 수집 |
|---|---|---|---|---|
| 1. 정적 파싱 | 0.18 | 0 | 0 | **0/4** |
| 2. 렌더 파싱 | 29.19 | 0 | 0 | 4/4 |
| 3. OCR 텍스트만 | 32.94 | 1,110 | 839 | 글자 1,354자 |
| 4. OCR + 분류 | 34.89 | 2,240 | 1,316 | 4/4, **13개 항목 전부 채움** |

LG 의 29초는 측정 방식 탓이 크다. `networkidle` 을 25초까지 기다렸는데 이 페이지는 그 상태에
도달하지 않아 대기가 끝까지 찼다. 저장소의 렌더러는 항목이 나타나면 진행한다.

## 캡처 대기를 바꿔 다시 잰 값 (LG)

| 대기 방식 | 초 | 이미지 | 읽힌 글자 | 입력 토큰 |
|---|---|---|---|---|
| 내용 셀렉터만 기다림 | 2.13 | 145KB | 1,353자 | 1,095 |
| 셀렉터 + 1.5초 | 3.15 | 145KB | 1,363자 | 1,095 |
| 셀렉터 + 3초 | 3.54 | 145KB | 1,372자 | 1,095 |

**캡처는 3초대에 끝난다.** 29초가 아니다. 다만 셀렉터만 기다린 회차에서 문서 높이가 아직
900px(뷰포트 그대로)로 잡히는 것이 관측됐고, 별도 회차에서는 21KB짜리 잘린 캡처가 나왔다.
**대기가 부족하면 조용히 잘린다.** 셀렉터 확인 뒤 1.5초 정도를 더 두는 편이 안전하다.

## 읽은 것

**시간은 캡처가 지배한다.** 모델 호출은 텍스트 추출 3.4~4.2초, 분류 2.5초다. 캡처 대기를
어떻게 잡느냐가 전체 시간을 정한다.

**토큰은 크지 않다.** 공고 하나에 입력 2,240~2,294, 출력 1,316~1,330. 이미지가 길어지면 입력이
타일 수에 비례해 는다. 단가는 바뀌므로 현재 Gemini 문서에서 확인해야 한다
(`.claude/rules/llm.md`).

**분류가 OCR 을 쓰는 이유다.** 셀렉터는 등록된 필드 4개만 준다. 같은 화면에서 분류는 13개
항목을 채웠다 — LG 는 13개 전부, 롯데는 12개. 셀렉터를 13개로 늘리려면 사이트마다 13번 맞춰야
하는데, 분류는 화면을 읽고 있는 것만 채운다.

**정적으로 되는 곳에서 OCR 은 59배 느리다.** 롯데 0.18초 대 10.62초. 정적으로 4/4 가 나오는
페이지에 OCR 을 쓰는 것은 손해다.

**LG 는 API 가 더 낫다.** API 는 제목·회사·마감·본문·자격요건을 구조화해서 주고 토큰을 쓰지
않는다. 캡처해서 글자로 되돌리면 정확도는 떨어지고 호출이 둘 는다.

## 저장 용량

전체 페이지 JPEG 는 롯데 279KB, LG 145KB 였다. 앞서 잰 다른 LG 공고는 187KB 다.
공고당 150~280KB 로 보면 된다.

지금 216건이면 32~60MB. **이미지는 SQLite 밖에 둬야 한다.** DB 가 1.9MB 인데 이미지를 넣으면
스냅샷 내보내기·가져오기가 못 쓰게 된다. 파일로 두고 DB 에는 경로만 남긴다.
