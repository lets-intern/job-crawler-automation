# 사이트 레시피

사이트 하나를 다루면서 알아낸 것을 파일 하나에 남긴다. 다음에 그 사이트가 깨졌을 때 처음부터
다시 알아내지 않기 위한 기록이다.

`.claude/site-recipes/<도메인>.md` 한 사이트 한 파일. 문서 규칙은 `.claude/rules/writing.md`.

## 언제 쓰는가

- 셀렉터 생성이 끝났을 때 (`selector-generate` 6단계)
- 정적 fetch 로 안 되는 것을 확인했을 때
- 워크플로우가 깨져서 원인을 밝혔을 때

세 번째가 제일 중요하다. 같은 사이트는 같은 이유로 두 번 깨진다.

## 양식

```markdown
# <사이트 이름> (<도메인>)

- 리스트 URL: <URL>
- 상세 URL 패턴: <패턴>
- 렌더링: 정적 / Playwright 필요 (근거: <무엇을 보고 판단했는지>)
- 페이지네이션: <쿼리 파라미터 또는 없음>
- 날짜 포맷: <원본 형태> → <정규화 규칙 이름>
- robots.txt: 허용 / 해당 경로 차단
- 권장 주기: <시간>

## 셀렉터 특이사항

<왜 그 셀렉터인지. 함정이 있으면 그 함정.>

## 이력

| 날짜 | 일 | 원인 | 조치 |
|---|---|---|---|
| 2026-08-21 | 최초 등록 | | |
```

## 쓸 때 지킬 것

**판단 근거를 같이 쓴다.** "Playwright 필요" 만 있으면 다음 사람이 다시 검증한다.
"정적 fetch 결과에 공고 제목 문자열 0건" 까지 쓰면 재검증이 필요 없다.

**셀렉터 전문을 복사해 두지 않는다.** 셀렉터는 DB 가 진실이고, 문서에 있는 사본은 반드시 낡는다.
특이사항과 이유만 쓴다.

**추측을 사실처럼 쓰지 않는다.** 확인 못 한 것은 확인 못 했다고 쓴다.

## 조회

```bash
ls .claude/site-recipes/
grep -rl "Playwright 필요" .claude/site-recipes/
```

새 사이트를 등록하기 전에 목록을 먼저 본다. 같은 채용 솔루션(그리팅, 잡코리아 임베드 등)을
쓰는 회사는 셀렉터가 거의 같다.
