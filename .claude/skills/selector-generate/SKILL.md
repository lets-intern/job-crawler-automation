# 셀렉터 생성

리스트 페이지 URL과 상세 페이지 URL을 받아 CSS 셀렉터 JSON을 만들고, **만든 그 HTML에 바로 돌려서**
매칭 결과까지 확인하는 절차다.

무엇을 해도 되는지는 이 스킬이 정하지 않는다. `.claude/rules/llm.md` 와
`.claude/rules/crawling.md` 가 정한다. 그 두 파일을 먼저 따른다.

## 절차

### 0. 기존 레시피 확인

같은 사이트를 이미 다룬 적이 있으면 거기부터 읽는다. 정적으로 안 되는 사이트, 페이지네이션 방식,
과거 실패 원인이 적혀 있다.

```bash
ls .claude/site-recipes/
```

### 1. 두 페이지 가져오기

공용 fetch 클라이언트로 가져온다. robots.txt 가 막고 있으면 여기서 멈추고 사용자에게 보고한다.
직접 `httpx.get` 을 부르지 않는다 (`rules/crawling.md`).

### 2. HTML 정제

- `script`, `style`, `svg`, 주석, 인라인 이벤트 핸들러 제거
- 리스트 페이지: 반복 구조를 찾아 **형제 3~4개만 남긴다**. 60개를 다 보내도 구조 정보는 같고 비용만 는다
- 정제 후에도 상한을 넘으면 영역을 좁힌다. 그냥 자르지 않는다

### 3. 셀렉터 생성 호출

스키마를 강제해서 JSON 으로 받는다.

```
list:   item, title, link, posted_at
detail: title, body, requirements, deadline, department
```

필드가 그 사이트에 없으면 `null` 로 둔다. 억지로 채우지 않는다.

### 4. 같은 HTML 로 즉시 검증

받은 셀렉터를 **2단계에서 정제하기 전 원본 HTML** 에 돌려 필드별 매칭 개수를 센다.

| 결과 | 판정 |
|---|---|
| item 매칭 0 | 실패. 재생성 1회 또는 수동 작성 |
| item 매칭 1개 뿐 | 의심. 리스트가 아니라 컨테이너를 잡았을 가능성 |
| item 매칭 정상, 일부 필드 0 | 부분 성공. 실패 필드 이름을 그대로 보고 |
| link 가 상대경로 | 정상. 절대 URL 변환은 파서 쪽 책임 |

매칭 0인 셀렉터를 성공으로 보고하지 않는다.

### 5. 결과 제시

셀렉터 JSON + 필드별 매칭 개수 + 실패 필드 목록을 함께 낸다. 사용자가 수정할 수 있게 JSON 그대로
보여준다.

### 6. 레시피 기록

새로 알아낸 사실(JS 렌더링 필요, 페이지네이션 파라미터, 날짜 포맷 등)이 있으면
`site-recipe` 스킬로 기록한다.

## 재생성 정책

응답이 깨졌을 때만 1회 재시도한다. 셀렉터가 매칭이 안 되는 것은 재생성으로 잘 안 고쳐진다 —
같은 HTML 에 같은 모델이면 대체로 같은 답이 온다. 이때는 수동 보정이 빠르다.

두 번 실패하면 사용자에게 판단을 넘긴다. 계속 돌리지 않는다.

## 하지 않는 것

- 워크플로우 등록. 그건 테스트 통과 후 사용자가 누른다
- 셀렉터를 매칭될 때까지 넓히기. `body` 를 잡는 셀렉터는 조용히 실패하므로 매칭 0보다 나쁘다
- 로그인/캡차 우회
