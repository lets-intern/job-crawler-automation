# 워크플로우 운영

등록된 워크플로우의 실행 상태를 보고, 문제 있는 것을 찾아 멈추거나 주기를 조정한다.

`.claude/rules/crawling.md` (스케줄러·동시성)와 `.claude/rules/data-safety.md` (쓰기 권한)를
먼저 따른다.

## 첫 명령은 status 다

예외 없다. 무엇이 돌고 있는지 모르는 상태에서 중지·재개를 하지 않는다.

```bash
python -m app.cli workflow status
```

## 명령

| 인자 | 동작 |
|---|---|
| 없음 / `status` | 전체 워크플로우의 주기·마지막 실행·누적 성공/실패를 표로 낸다. 아무것도 바꾸지 않는다 |
| `failing` | 실패율이 임계치를 넘은 것만 추린다 |
| `pause <id>` | 스케줄에서 내린다. 진행 중 실행은 끝까지 둔다 |
| `resume <id>` | 다시 올린다 |
| `interval <id> <분>` | 주기를 바꾼다. DB 를 고치고 스케줄러에 반영한다 |
| `run <id>` | 지금 1회 실행한다. 주기와 무관 |

`pause`, `resume`, `interval`, `run` 은 **사용자가 명시적으로 요청했을 때만** 쓴다.
`status`, `failing` 은 언제든 쓴다.

## 실패율이 높을 때 판단 순서

1. `crawl_runs` 에서 최근 실패 몇 건의 `error_message` 를 본다 — 원인이 한 종류인지 섞였는지
2. 전송 실패만 계속이면 사이트 장애 또는 차단이다. 주기를 늘리고 관찰한다
3. 셀렉터 미스면 사이트 구조가 바뀐 것이다. 중지하고 `selector-generate` 로 넘긴다
4. 원인이 섞여 있으면 중지부터 한다. 원인 모르는 채로 계속 때리지 않는다

```bash
python -m app.cli workflow runs --workflow <id> --limit 10
```

## 주기를 정할 때

기본은 느린 쪽이다. 채용공고는 분 단위로 바뀌지 않는다. 6시간이 대부분의 사이트에 충분하고,
1시간 미만은 그 사이트가 정말 그만큼 자주 바뀐다는 근거가 있을 때만 쓴다.

동시 실행 상한은 워크플로우별 주기가 아니라 전역 세마포어가 정한다. 주기를 촘촘하게 해서
처리량을 올리려는 시도는 스킵 로그만 늘린다.

## 보고 형식

```
## 워크플로우 상태 (N개)
| id | 이름 | 주기 | 최근 실행 | 성공 | 실패 | 상태 |
[failing 있을 때] 실패 원인 분류와 권고 행동
```

## 하지 않는 것

- status 없이 중지·재개
- 사용자 요청 없이 주기 변경
- 실패 원인을 모른 채 재개
